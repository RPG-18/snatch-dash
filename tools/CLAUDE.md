# tools/ — вспомогательные скрипты

Инструменты для подготовки офлайн-данных навигации. К коду приложения отношения
не имеют: отдельный Python-конвейер со своими зависимостями
([`planetiler/requirements.txt`](./planetiler/requirements.txt)), в сборке APK не
участвует.

Отдельно — [`BRouter.md`](./BRouter.md): заметка про данные для будущей
офлайн-маршрутизации. Конвейера нет, но там записано, почему нарезанные по
субъектам `extracts/*.osm.pbf` **не годятся** ему на вход (у BRouter своя сетка
5°×5°, не совпадающая с субъектами) — чтобы это не выводили заново.

## Векторные тайлы в формате PMTiles

[`planetiler/`](./planetiler) — конвейер «выгрузка OSM с Geofabrik → PMTiles»:
один `.pmtiles` на регион плюс манифест `index.json`, по которому телефон
понимает, что скачать и не побилось ли оно в дороге. Включена одна страна —
Россия, режется на субъекты; последняя сборка (2026-09-01, вечер) — 84 файла,
4.34 ГиБ (4.66 ГБ по счёту `index.json`). Прежние «2.71 ГБ» — размер сборки с урезанными
полигонами, а не результат оптимизации: см. поправку в `minimization_ru.md`.

Что знать, прежде чем что-то менять:

- **Артефакты не в git.** `downloads/ polygons/ extracts/ out/ data/` и сам
  `planetiler.jar` — гигабайты, пересобираются с нуля (см.
  [`planetiler/.gitignore`](./planetiler/.gitignore)). Исходный `.osm.pbf`
  скачивается вручную: `source` в `regions.yaml` — просто ссылка, куда сходить,
  ни один скрипт по ней не ходит.
- **Пересборка полная, не инкрементальная.** `out/` удаляется целиком перед
  еженедельным прогоном; логики «обновить один регион» нет и не планируется,
  поэтому не нужна и чистка осиротевших файлов.
- **Правишь настройки размера — дописывай запись в `minimization_ru.md`.** Это
  журнал, а не отчёт: следующему важно видеть не только что отключили, но и что
  пробовали не отключать и почему (`water`, `building`, `maxzoom` — там есть
  список с причинами).
- **Код региона берётся из имени файла:** `ru-mow.osm.pbf` → `ru-mow`. `Path.stem`
  здесь не годится — снимет только `.pbf` и даст `ru-mow.osm`; нужен
  `name.removesuffix(".osm.pbf")`. На этом уже спотыкались дважды, и оба раза
  молча: конфиг переставал применяться, а файл — попадать под маску.
- **Java 21+, не 17.** Наш `planetiler.jar` содержит классы major 65; на Java 17
  он падает с `UnsupportedClassVersionError` ещё до чтения данных.
- **Полигон субъекта — ровно одна релация.** Overpass на `(._;>>;)` отдаёт
  полное замыкание, вместе с вложенными subarea-релациями муниципальных округов.
  Если записать их в `polygons/<код>.osm`, `osmium extract -p` сольёт площади
  всех релаций файла в одну, вложенные кольца станут дырами, и субъект потеряет
  территорию под муниципалитетами: у Курганской области — 25 234 ноды вместо
  4 108 905. Пишет только топ-релацию `fetch_boundaries.build_osm_xml`, там же
  замеры и ссылка на man osmium-extract, где перекрытие полигонов объявлено
  undefined behaviour. Ровно это испортило сборку 2026-08-31.
- **`polygons/` со сборки 2026-08-31 протухли.** Они скачаны до этого фикса, и
  77 из 83 содержат subarea. Существующий файл скрипт не перекачивает — нужен
  `fetch_boundaries.py --force`, иначе пересборка повторит урезанные паки.
- **`validate_packs.py` ловит только полную потерю территории.** Порог бинарный:
  слой либо есть, либо нет. Урезанный наполовину пак проходит — уцелевших
  городов хватает на весь обязательный набор слоёв. На сборке 2026-08-31 все 84
  пака были OK, при том что в `ru-bel` осталось 9% нод области.
- **Overpass может врать молча.** При таймауте он отдаёт HTTP 200 и валидный
  JSON с неполными `elements` и полем `remark`; `fetch_boundaries.py` это
  проверяет. Поломки сборки 2026-08-31 вызваны не им — ответы были целыми,
  сверено с локальным дампом через `osmium getid -r`; проверка стоит как
  профилактика.
- **Чукотка — два файла** (`ru-chu` + `ru-chu-east`): её граница пересекает 180-й
  меридиан, и без разреза planetiler печёт океанские тайлы через все 360°
  долготы. Любой код, который считает «один субъект = один файл», это сломает.
