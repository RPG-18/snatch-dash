# Сервер карт: формат данных и протокол скачивания

Контракт между генератором тайлов ([`tools/planetiler`](../tools/planetiler)) и
приложением: в каком виде лежат карты на сервере, как устроен манифест и как
клиент качает пак, не получив при этом склейку из двух сборок.

Почему офлайн-карты вообще появились и чем рисуются — [`docs/offline_mode_ru.md`](../docs/offline_mode_ru.md), §8.
Как устроена сборка — [`tools/planetiler/README.md`](../tools/planetiler/README.md).
Как из пака получается кадр на приборке — [`drawing_from_local_tiles.md`](./drawing_from_local_tiles.md).

Терминология: **пак** — один `.pmtiles` (обычно один субъект РФ). В интерфейсе
слово «пак» не показывается — райдер скачивает «Ленинградскую область».

## Формат тайлов

**PMTiles v3** с векторными тайлами **MVT** по схеме **OpenMapTiles**.

| Свойство | Значение | Откуда следует |
|---|---|---|
| Контейнер | PMTiles v3, один файл на регион | [спека формата](https://github.com/protomaps/PMTiles/blob/main/spec/v3/spec.md) |
| Тайлы | MVT (`tile_type = 1`), сжаты gzip (`tile_compression = 2`) | заголовок пака |
| Схема | OpenMapTiles, встроена в planetiler | `vector_layers` в метаданных пака |
| Зумы | 11–14 (`minzoom`/`maxzoom` из `planetiler.yaml`) | z14 — потолок детализации, выше рендер оверзумит сам; z11 — нижняя ступень лестницы зумов дэша. Ниже z11 тайлов нет: клиент туда уходить не должен — будет пустой экран, а не грубая карта |
| Языки подписей | `ru`, `en` | `languages` в `planetiler.yaml` |
| Проекция | Web Mercator, slippy-раскладка, порядок тайлов — кривая Гильберта | формат PMTiles |

Из корпуса **глобально исключены** `landcover`, `housenumber`, `water_name`,
`mountain_peak` (`defaults` в `planetiler.yaml`). Для стиля это означает: фоновой
заливки леса и полей в данных нет, фон рисует сам рендер.

Почему PMTiles, а не MBTiles: один файл читается и локально, и по HTTP Range без
тайл-сервера, а MapLibre Native понимает схему `pmtiles://` сам, начиная с
Android 11.8.0 — обвязку писать не нужно.

Опубликованный корпус (сборка 2026-09-01): 84 файла, 4.66 ГБ, медиана 40 МБ на
регион, от 2.8 МБ (Ингушетия) до 344 МБ (Якутия). Локально уже собран следующий
(2026-09-02, новая схема, `minzoom: 11`): 84 файла, 4.62 ГБ, медиана 42 МБ, от
3.1 до 356 МБ — свойства ниже появятся у паков вместе с его публикацией. Чукотка — два файла (`ru-chu` и
`ru-chu-east`), она пересекает 180-й меридиан; любой код, считающий «один
субъект = один файл», на ней сломается.

**Что даёт клиенту новая схема сборки** (паки вырезаются из сборки всей страны
по границе субъекта, см. [`tools/planetiler/README.md`](../tools/planetiler/README.md);
собрано локально, в опубликованном корпусе этого ещё нет):

- **Пак обрезан по границе субъекта плюс буфер 2 км.** Соседние паки поэтому
  перекрываются полосой в пару километров: карта не обрывается на границе, даже
  если сосед не скачан. Тайлов за пределами этой полосы в паке нет вовсе —
  раньше туда попадал океан по всему bbox экстракта (у Ленинградской области это
  была треть файла), и на одну и ту же клетку у берега отвечали до восьми паков
  сразу.
- **`bounds` в заголовке пака теперь честный** — это bbox границы субъекта с
  буфером, а не раздутый океаном прямоугольник (у `ru-len` было 13.6–37.9° в. д.
  вместе с Балтикой у Германии, стало 26.4–35.7°). По нему можно выбирать, какие
  паки держать активными. Исключение — Чукотка: у её половин bbox честный, но
  единым файлом она бы дала bbox во весь мир, потому что TileJSON запрещает
  bbox, заворачивающийся через антимеридиан.
- **Подпись объекта, лежащего в двух субъектах, есть только в одном паке.**
  Схема OpenMapTiles ставит её в point-on-surface объекта: у Кавказского
  заповедника это Краснодарский край, поэтому в паке Адыгеи его полигон без
  названия. При нескольких активных паках это не видно.

## Раскладка на сервере

```
<база>/index.json
<база>/ru/ru-mow.pmtiles
<база>/ru/ru-chu.pmtiles
<база>/ru/ru-chu-east.pmtiles
```

Подкаталог на страну. Базовый URL клиент подставляет сам — в манифесте лежат
только относительные пути.

Что отдаёт хостинг (проверено на боевом бакете): `accept-ranges: bytes`,
`content-type: application/octet-stream`, `ETag`, `Last-Modified`. Авторизации
нет. Обязательна атрибуция © OpenStreetMap на каждом экране с картой.

## `index.json`

```json
{
  "version": 1,
  "generated_at": "2026-09-01T04:53:22Z",
  "file_count": 84,
  "total_size": 4658602049,
  "countries": [
    {
      "iso": "ru",
      "mode": "subjects",
      "regions": [
        {
          "code": "ru-ad",
          "path": "ru/ru-ad.pmtiles",
          "size": 8983922,
          "sha256": "7ad6b17aef162b3744adde579ee3b85f00334297d840f56010561b1847275b98"
        }
      ]
    }
  ]
}
```

| Поле | Смысл для клиента |
|---|---|
| `version` | версия **схемы манифеста**, не данных. См. «Совместимость» |
| `generated_at` | UTC-момент сборки индекса; токен состояния всего корпуса |
| `file_count`, `total_size` | агрегаты для UI («скачать всё — N файлов, X ГБ») без обхода списка |
| `iso`, `mode` | страна и режим нарезки (`subjects` — по субъектам, `whole` — одним файлом) |
| `code` | идентификатор региона, он же имя файла без расширения |
| `path` | путь относительно базы, не абсолютный URL |
| `size` | ожидаемый размер в байтах |
| `sha256` | хеш содержимого файла; токен версии **конкретного пака** |

Чего в манифесте намеренно нет — **отображаемых имён**. Приложение двуязычное, а
генератор тайлов не должен знать про локализацию: «Ленинградская область» /
«Leningrad Oblast» берутся из таблицы на стороне приложения по `code`.

### Совместимость

- **`version` растёт только при ломающем изменении.** Добавление нового
  необязательного поля версию не поднимает, поэтому **клиент обязан игнорировать
  незнакомые поля** — иначе первое же добавление сломает установленные версии
  приложения.
- **Незнакомый `version` — это отказ, а не догадка.** Больше известного —
  сообщить «обновите приложение» и не трогать установленные паки; парсить
  манифест «как получится» нельзя.

## Скачивание: упрощённая оптимистичная блокировка

**Проблема.** Корпус пересобирается целиком раз в неделю: `out/` удаляется,
каждый пак печётся заново. Planetiler пишет в метаданные тайлсета время сборки,
поэтому **sha256 меняется даже если данные OSM не изменились** — после каждой
пересборки отличаются все 84 файла. Клиент читает манифест, начинает качать
114 МБ, а публикация происходит в этот момент: докачанные байты будут уже из
новой сборки, а ожидаемый sha256 — из старого манифеста.

**Решение — оптимистичная блокировка.** Сервер ничего не блокирует и о клиентах
не знает; клиент берёт версию, работает, а конфликт обнаруживает при «коммите»,
то есть при проверке хеша после скачивания. Роль версии играют два токена:

- `generated_at` — версия **всего корпуса**, дешёвая проверка «менялось ли хоть
  что-нибудь»;
- `sha256` региона — версия **конкретного пака**, по нему и происходит
  обнаружение конфликта.

**Почему «упрощённая».** Полноценной блокировке пришлось бы обеспечивать
согласованность набора паков между собой. Здесь она не нужна: каждый пак
самодостаточен, перекрёстных ссылок между ними нет, поэтому `ru-len` от одной
сборки и `ru-spe` от другой прекрасно работают вместе. Максимум, что даёт
разнобой сборок, — чуть разная геометрия дороги на самой границе субъектов, если
её в OSM успели поправить между сборками. Косметика, а не рассогласование.
Отсюда: **блокировка на уровне отдельного файла, корпусной атомарности не
требуется.**

### Порядок скачивания одного пака

1. Прочитать `index.json`, запомнить как ожидаемое: `generated_at` корпуса и
   `size` + `sha256` нужного региона.
2. Скачать `<база>/<path>` во временный файл `<code>.pmtiles.part`.
3. Посчитать sha256 полученных байт.
4. **Совпал** — атомарно переименовать `.part` в `<code>.pmtiles` и записать в
   реестр установленных: `code`, `sha256`, `generated_at` того манифеста, размер,
   время установки.
5. **Не совпал** — это ещё не повреждение. Перечитать `index.json`:
   - `generated_at` изменился → корпус пересобрали во время скачивания, это
     штатный конфликт. Повторить с новым ожидаемым `sha256`;
   - `generated_at` тот же → настоящая порча: сбой передачи или сломанный
     бакет. Сообщить пользователю, `.part` удалить, вслепую не повторять.
6. Ограничить число повторов (двух достаточно) — иначе сервер, публикующий в
   цикле, заставит клиент качать бесконечно.

### Обязательные детали, без которых схема не работает

**Атомарная установка.** Качать в `.part`, проверять хеш, только потом
переименовывать. `pmtiles://file://` откроет и обрезанный файл, и покажет
половину карты без единой ошибки — ровно тот класс отказов, на который уже
наступали в конвейере (см. `validate_packs.py`). Тот же приём уже применяется в
`build_index.py` (`os.replace`) и в `TileProvider.writeDiskAtomic`.

**Докачка только с `If-Range`.** При возобновлении по `Range` без условия можно
склеить начало старой сборки с хвостом новой — файл будет нужного размера и
битым по содержимому. Проверено на боевом бакете:

| Запрос | Ответ |
|---|---|
| `Range: bytes=0-99` | `206`, `content-range: bytes 0-99/2925442` |
| `Range` + `If-Range` с текущим ETag | `206`, докачка продолжается |
| `Range` + `If-Range` с устаревшим ETag | **`200`, тело целиком (2 925 442 Б)** |

То есть ETag надо сохранять вместе с `.part` и отдавать в `If-Range` — тогда
пересборка на сервере автоматически превращает докачку в полную перезакачку, а
не в тихую склейку.

**Проверка места до старта.** `size` из манифеста известен заранее; отказ по
свободному месту должен случаться до скачивания, а не на 90%.

### Проверка обновлений

1. Скачать только `index.json`, сравнить `generated_at` с сохранённым. Не
   изменился — всё свежее, дальше не ходить.
2. Изменился — сравнить `sha256` каждого установленного пака с манифестом;
   перекачивать только разошедшиеся.

**Честно про пункт 2:** поскольку время сборки попадает в метаданные тайлсета,
после еженедельной пересборки разойдутся **все** паки. То есть «обновление» на
практике означает перекачать всё установленное заново. Интерфейс не должен
обещать инкрементальность и обязан оставлять решение за пользователем — 130 МБ
на пару «город + область» (Петербург с Ленобластью) по мобильной сети
пользователь должен подтвердить сам.

## Публикация (сторона сервера)

Заливка во временный каталог, затем атомарное переключение на боевой через API
хостинга. Требование к порядку одно: **`index.json` публикуется последним.**
Иначе между появлением нового манифеста и заливкой файлов клиенты получат
ожидаемые sha256, которым ещё ничего не соответствует, — и весь протокол выше
выродится в цикл «не совпало → перечитать → не совпало».
