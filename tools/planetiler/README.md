# tools/planetiler — офлайн-тайлы в PMTiles

Конвейер, который превращает выгрузки OpenStreetMap с Geofabrik (`.osm.pbf`) в
векторные тайлы **PMTiles** — по одному файлу на регион — и собирает манифест
`index.json`, по которому телефон понимает, что скачать и не побилось ли оно в
дороге. Схема тайлов — OpenMapTiles, она встроена в сам planetiler.

Зачем: навигация на дэше должна работать там, где связи нет. Один `.pmtiles` на
субъект РФ — это самодостаточный офлайн-пак: положил на телефон, и карта
рисуется без сети.

**Как это устроено с 2026-09-02:** planetiler запускается **один раз на страну**,
а пак каждого субъекта **вырезается** из этой сборки (`pmtiles extract --region`)
по границе, расширенной буфером в 2 км. Нарезки OSM перед сборкой больше нет.
Почему так — в докстринге [`build_pmtiles.py`](./build_pmtiles.py) и в
[`todo.md`](./todo.md); коротко: впятеро быстрее (11 мин против 55) и кривая
граница больше не может молча урезать данные, потому что данные к моменту
нарезки уже собраны.

Сейчас включена одна страна — **Россия**, режется на субъекты (кроме Чукотки, см. `exclude`).

Текущая сборка (2026-09-03, склейка двух агломераций, Чукотка исключена) —
**80 файлов на 4.14 ГиБ (4.45 ГБ)**, медиана 41 МБ на регион, от 3.1 МБ
(Ингушетия) до 356 МБ (Якутия); 80/80 прошли `validate_packs.py`. Нарезка
80 паков — 39 с поверх готовой `full/ru.pmtiles` (сборка страны, 8 мин 52 с,
не переделывалась).
Она же опубликована на бакете и проверена после заливки: 81 объект, HTTP 200 на
всех 80 паках, sha256 скачанного пака совпал с манифестом.

Прежние «2.71 ГБ» относятся к сборке 2026-08-31, где субъекты были урезаны
битыми полигонами, — это не базовая линия.

Что чем настраивается:

| Файл | Отвечает за |
|---|---|
| [`regions.yaml`](./regions.yaml) | **что** собираем: страны, режим нарезки, ссылки на исходники |
| [`planetiler.yaml`](./planetiler.yaml) | **как** собираем: флаги planetiler на страну (уровня субъекта больше нет) |

## Что нужно поставить

**Python 3.9+** (сами скрипты + PyYAML и shapely), **osmium-tool** (перевод
границы субъекта в GeoJSON), **Java 21+ и `planetiler.jar`** (сборка тайлов;
именно 21 — классы в jar имеют версию формата 65, на 17 будет
`UnsupportedClassVersionError`), **pmtiles CLI** (вырезание паков из сборки
страны). Пошаговая установка на Linux/macOS/Windows и подбор памяти/потоков под
конкретную машину — в [`tools/README.md`](../README.md).

Проверить, что всё на месте:

```bash
python3 --version   # 3.9+
osmium --version    # osmium-tool
java -version       # 21+ (проверено на OpenJDK 21.0.12)
pmtiles --version   # pmtiles CLI (проверено на 1.31.2)
```

`planetiler.jar` качается одним файлом с
[GitHub Releases](https://github.com/onthegomap/planetiler/releases), собирать
ничего не нужно; путь к нему передаётся через `PLANETILER_JAR`.

## Как запустить (Россия)

**Шаг 0.** Скачать исходник вручную — по ссылке из `source` страны `ru` в
[`regions.yaml`](./regions.yaml) — и положить в `downloads/ru-latest.osm.pbf`.
Это несколько ГБ, лучше браузером или менеджером закачек с докачкой при обрыве,
а не `curl`/`wget` без `-C -`. Ни один скрипт конвейера этот файл сам не тянет:
`source` — просто ссылка, куда сходить руками.

```bash
cd tools/planetiler
pip install -r requirements.txt

# 1. Границы субъектов через Overpass -> polygons/<code>.osm
python3 fetch_boundaries.py --only ru

# 2. Тайлы всей страны одним прогоном -> full/ru.pmtiles
JAVA_TOOL_OPTIONS="-Xmx10g" PLANETILER_THREADS=8 \
  PLANETILER_JAR=/path/to/planetiler.jar python3 build_pmtiles.py --only ru

# 3. Паки субъектов -> out/ru/<код>.pmtiles (буфер вокруг границы — 2 км)
python3 cut_packs.py --only ru

# 4. Манифест -> out/index.json
python3 build_index.py --only ru

# 5. Проверка: не потерял ли какой-нибудь пак часть субъекта
python3 validate_packs.py --only ru
```

Сколько это занимает (замерено на MacBook Pro M3 Pro, 18 ГБ, 8 потоков):

| Шаг | Время | Замечания |
|---|---|---|
| 1. Границы | десятки минут | ~85 последовательных запросов к публичному Overpass с паузой между ними |
| 2. Тайлы страны | 8 мин 52 с на всю Россию | пик RSS 8.6 ГБ, ~20 ГБ временных на диске, +~1.4 ГБ разовой подкачки на первом запуске |
| 3. Паки | 39 с на 80 паков | `osmium export` границы плюс сам вырез (доли секунды на пак) |
| 4. Манифест | секунды | sha256 идёт сотни МБ/с |
| 5. Проверка | 1 мин 20 с локально, ~2 мин по HTTP | по HTTP читает только заголовки и метаданные; локально ещё и тайлы — проверка по городам (`--cities off`, если не нужна) |

Итого полная пересборка России (шаги 2-5, границы уже скачаны) — **11 минут**
против ~55 у прежней схемы с `osmium extract` и 84 прогонами planetiler.

**Все шаги идемпотентны**: уже скачанные границы пропускаются (`--force` у
`fetch_boundaries.py` — перекачать), шаги 2-5 просто перезаписывают свой выход.
Оборванный прогон достаточно запустить заново. Ровно одного они не делают —
не удаляют пак, который выпал из набора (субъект уехал в группу `merge`);
шаг 5 такой осколок находит, снести файл нужно руками. Шаг 3 не требует шага 2, если
`full/<iso>.pmtiles` уже лежит на месте: перерезать паки с другим `--buffer-km`
или после перекачки одной границы — минута, а не пересборка.

**Ключи скриптов.** У всех есть `--only <iso[,iso...]>` (ограничиться странами),
`--verbose` и `--help`. У `fetch_boundaries.py` дополнительно
`--code <iso3166-2>` (например `ru-kgd`) — скачать границу ровно одного субъекта
по тегу, без обхода всей страны: удобно для точечной перекачки и для проверки
конвейера на одном маленьком регионе.

**Прогресс.** Везде, где идёт цикл по регионам, в лог печатается счётчик `[i/N]`;
planetiler на шаге 2 пишет свой прогресс сам. Хеширование в `build_index.py`
прогресс внутри файла не показывает намеренно — на наших размерах это доли
секунды.

## Как устроено

| Шаг | Скрипт | Вход → выход |
|---|---|---|
| 1 | *вручную* | Geofabrik → `downloads/<iso>-latest.osm.pbf` |
| 2 | `fetch_boundaries.py` | Overpass → `polygons/<code>.osm` (только `mode: subjects`) |
| 3 | `build_pmtiles.py` | `downloads/<iso>-latest.osm.pbf` → `full/<iso>.pmtiles` |
| 4 | `cut_packs.py` | `full/<iso>.pmtiles` + `polygons/` → `out/<iso>/<код>.pmtiles` (с учётом `merge`/`exclude`) |
| 5 | `build_index.py` | обход `out/` → `out/index.json` |
| 6 | `validate_packs.py` | `out/` или бакет → отчёт о проблемных паках, код возврата 1 |
| 7 | *отдельно* | публикация `out/` на сервер — вне этого каталога |

```
tools/planetiler/
  regions.yaml            # конфиг стран/регионов
  planetiler.yaml         # настройки planetiler (языки/зум/упрощение/слои)
  requirements.txt        # pip-зависимости (PyYAML и shapely)
  common.py               # общее: чтение regions.yaml, пути, логирование
  fetch_boundaries.py     # Overpass -> polygons/<code>.osm
  build_pmtiles.py        # planetiler x1 на страну -> full/<iso>.pmtiles
  cut_packs.py            # вырезы по границам -> out/<iso>/<код>.pmtiles
  build_index.py          # sha256+size -> out/index.json (атомарно)
  validate_packs.py       # проверка готовых паков (структура/слои/комплектность)
  downloads/ polygons/ full/ out/ data/   # артефакты, не в git (.gitignore)
```

Скрипты — на Python, а не shell, чтобы конвейер одинаково работал под
Windows/macOS/Linux и мог читать YAML.

### Границы (шаг 2)

Через Overpass тянутся релации `admin_level = subject_admin_level` внутри страны;
каждая сохраняется как отдельный `.osm`-файл, названный по тегу `ISO3166-2` в
нижнем регистре (`RU-MOW` → `polygons/ru-mow.osm`).

Формат **`.osm` (OSM XML), а не geojson**: osmium умеет сам собрать
(мульти)полигон границы из релации в таком файле — не нужно вручную склеивать
outer/inner кольца средствами Python. GeoJSON, который нужен `pmtiles extract`,
делается из него на шаге 4 одной командой `osmium export`.

В файл пишется **ровно одна релация** — сама граница субъекта, плюс её way-члены
и их узлы. Замыкание `(._;>>;)`, которое возвращает Overpass, содержит ещё и
вложенные subarea-релации муниципальных округов; если оставить их в файле,
osmium сольёт площади всех релаций файла в одну, вложенные кольца станут дырами,
и субъект потеряет территорию под муниципалитетами — у Курганской области
выходило 25 234 ноды вместо 4 108 905 (тогда это ломало сами данные, теперь
испортило бы только форму выреза, но проверка всё равно нужна). Замеры и ссылка на
man osmium-extract, где перекрытие полигонов объявлено undefined behaviour, — в
докстринге `build_osm_xml`.

Релации **без тега `ISO3166-2` пропускаются с предупреждением** — ручного
сопоставления в конвейере нет. Из-за этого в сборке 83 субъекта, а не 89.

Запрос идёт к зеркалу VK Maps: основной `overpass-api.de` на таких запросах
часто отдаёт 504. Фильтр — по префиксу тега `ISO3166-2` (`^RU-`), а не по
area-пивоту страны: area-пивот не укладывается в лимит времени публичных зеркал.
Bbox не задаётся намеренно — иначе потерялись бы субъекты восточнее 180°.

### Тайлы страны (шаг 3)

planetiler запускается **один раз на страну** по `downloads/<iso>-latest.osm.pbf`.
Настроечные флаги вынесены в [`planetiler.yaml`](./planetiler.yaml); сам скрипт
добавляет только то, что от региона не зависит:

- `--osm-path` / `--output` — структурные, знает только скрипт;
- `--download` — профиль OpenMapTiles требует три глобальных вспомогательных
  датасета (береговые линии озёр, полигоны воды, Natural Earth — фон низких
  зумов), без них planetiler падает ещё до чтения `.osm.pbf`. Качается один раз
  (~1.4 ГБ) в `data/sources/` и переиспользуется дальше;
- `--threads` — машино-зависимая настройка, берётся из `PLANETILER_THREADS`,
  а не из YAML (иначе конфиг зависел бы от железа).

**Память не ограничивает, ограничивает диск.** planetiler по умолчанию держит
данные в mmap-файлах (`storage=mmap`, `nodemap_type=sparsearray`), в RAM у него
300 МБ индекса — столько же на России, сколько на одном субъекте. На Россию он
просит ~20 ГБ временных файлов плюс ~5 ГБ под выход и печатает свою оценку в
начале лога (уровень DEBUG). Замер: 8 мин 52 с, пик RSS 8.6 ГБ при `-Xmx10g`.

**Чем платим за единственный прогон.** Флаги теперь общие на страну: задать
отдельному субъекту своё упрощение или `maxzoom` нельзя — таких субъектов в
конфиге больше нет. Если понадобится исключение (скажем, `maxzoom: 15` для
одного города), его придётся собирать отдельным прогоном planetiler мимо этой
схемы.

### Паки субъектов (шаг 4)

`cut_packs.py` вырезает из `full/<iso>.pmtiles` по паку на субъект (или на
группу склеенных субъектов, см. ниже):
`polygons/<код>.osm` → `osmium export` → GeoJSON → `pmtiles extract --region`.
Тела тайлов при этом копируются как есть, поэтому внутренность пака бит-в-бит
совпадает со сборкой страны, а лишние тайлы (океан на весь bbox экстракта) в
пак просто не попадают. Полный корпус режется примерно за минуту.

Отданный `extract` полигон остаётся рядом с границей как
`polygons/<код>.region.geojson` — по нему видно, что именно вырезали.

**Буфер вокруг границы — 2 км по умолчанию (`--buffer-km`).** Резать ровно по
границе нельзя: у райдера с одним скачанным паком карта оборвётся ровно на ней.
Замер по тогдашнему паку Петербурга (`ru-spe`, до склейки), число features в
тайле z14:

| точка | прежняя схема | буфер 0 | буфер 2 км | буфер 5 км |
|---|---:|---:|---:|---:|
| Мурино, ~1 км за КАД | 41 | нет тайла | 1806 | 1806 |
| Всеволожск, ~5 км | 1 | нет тайла | нет тайла | 622 |

То есть без буфера пропадают даже обрывки, которые были раньше. Цена по корпусу:
2 км — +3.4%, 5 км — +8.1%; платят маленькие субъекты с длинной границей
(Адыгея +66%, Москва +40% — обе мерились отдельными паками, до склейки), дальние
большие — почти ноль (Якутия +0.8%).

**Склейка субъектов — `merge` в [`regions.yaml`](./regions.yaml).** Город
федерального значения и окружающая его область — одна агломерация и одна поездка,
поэтому они собираются в один пак:

| Пак | Что внутри | Раздельно было | Стало |
|---|---|---:|---:|
| `ru-len-spe` | Ленинградская область + Санкт-Петербург | 128.8 МБ | 113.1 МБ (−12.2%) |
| `ru-mos-mow` | Московская область + Москва | 198.1 МБ | 168.9 МБ (−14.7%) |

Границы частей объединяются (`unary_union`), буфер кладётся уже вокруг
объединения. Экономия — это перекрытие, которое при раздельной нарезке шло
дважды: буфер по обе стороны общей границы плюс обзорные тайлы z11, накрывающие
сразу обоих соседей. Райдеру она достаётся вся: на агломерацию он раньше качал
оба пака.

Обрезка получается **по внешней границе области** в обоих случаях, но по разной
причине. Петербург целиком лежит в дыре Ленинградской области — объединение
просто закрывает дыру. Москва не анклав: Новомосковский и Троицкий округа
доходят до внешнего края области у Калужской, так что объединение больше области
по площади, но не по bbox. Ни у одной из групп bbox от склейки не вырос.

Границы частей по-прежнему качаются и лежат в `polygons/` по отдельности —
склейка происходит на шаге нарезки, а не на шаге границ. Объединённый полигон
пишется рядом как `polygons/<код группы>.geojson`: по нему `validate_packs.py`
проверяет города.

**Код пака перестал быть кодом субъекта.** `ru-len-spe` — не ISO 3166-2, и
субъектов в `polygons/` 83, а паков 80. Ожидаемый набор паков считает
`common.pack_plan` — единственное место, где применяются `merge` и `exclude`.
А вот `out/ru/ru-len.pmtiles` от прошлой сборки `cut_packs.py` не удаляет — его нужно снести руками, иначе `build_index.py`
возьмёт в манифест и склейку, и осколок. `validate_packs.py` на такое ругается
«лишние паки» и возвращает 1, так что до публикации это не доедет.

**Исключение субъекта — `exclude` в [`regions.yaml`](./regions.yaml).** Сейчас
там один код: `ru-chu`, Чукотка.

Она пересекает 180-й меридиан, а TileJSON запрещает `bounds`, заворачивающийся
через антимеридиан: у цельного пака (136.2 МБ) он вырождается во весь мир, и
такой пак отвечал бы на любой тайл планеты. Поэтому Чукотка собиралась двумя
файлами, `ru-chu` (запад, 82.0 МБ) и `ru-chu-east` (восток, 45.3 МБ), — и это
единственное место, где ломалось правило «один субъект = один пак»: его
приходилось держать в голове и на клиенте, и в каждой проверке конвейера. Ради
127 МБ на 48 тысяч жителей и единственную дорогу — не стоит того, убрана целиком.

Граница `polygons/ru-chu.osm` при этом **качается и остаётся на месте**: по ней
проверяется, что код в `exclude` не опечатка. Код разбиения на половины
(`split_at_antimeridian`) тоже цел — вернуть Чукотку значит убрать одну строку из
`exclude`, и без этого кода возврат дал бы цельный пак с bbox во весь мир, причём
молча.

**Подписи трансграничных объектов.** Схема OpenMapTiles ставит подпись площадного
объекта в его point-on-surface (`features.pointOnSurface(...)` в `Park.java`), и
теперь эта точка одна на всю страну, а не по одной на каждую сборку субъекта.
Кавказский заповедник тянется через Адыгею и Краснодарский край — его подпись
лежит в паке Краснодарского края, и в паке Адыгеи полигон остаётся без названия.
На дэше это не видно, пока активны оба соседних пака; заметно только тому, кто
скачал ровно один.

### Проверка (шаг 6)

Конвейер умеет собрать формально исправный, но дырявый пак: sha256 в манифесте
верный, PMTiles читается, а внутри нет половины субъекта. Именно так вышло на
сборке 2026-08-31 — из-за вложенных subarea-релаций в файле полигона (шаг 2,
исправлено в `build_osm_xml`).

Второй возможный механизм — обрезанный ответ Overpass: при таймауте он отдаёт
**HTTP 200** и валидный JSON, в котором часть `elements` просто отсутствует, а в
поле `remark` лежит «runtime error: Query timed out». `fetch_boundaries.py` такой
ответ распознаёт (`remark` → ретрай, а если не помогло — субъект пропускается с
ошибкой в логе, но неполная граница на диск не пишется).

`validate_packs.py` проверяет уже собранное:

```bash
python3 validate_packs.py                    # локальный out/
python3 validate_packs.py --base-url https://storage.yandexcloud.net/snatch-dash-maps/
```

Проверяет четыре вещи: структуру (PMTiles v3, тип тайлов MVT, `minzoom` и
`maxzoom` из `planetiler.yaml`), набор слоёв (базовый набор OpenMapTiles минус
то, что отключено через `exclude_layers`), **города** (у каждого НП внутри
границы есть дороги на `maxzoom`) и комплектность (каждой границе в `polygons/`
соответствует пак). Первые две и последняя читают только заголовок и метаданные —
по HTTP это range-запросы на пару килобайт.

Ключевая из трёх — проверка слоёв: потеря территории почти всегда означает
потерю городов, а без застройки не бывает `building`/`housenumber`. На сборке
2026-08-31 она дала 6 проблемных паков из 84: `ru-kgn` (Курганская, нет города
Кургана вообще), `ru-mag`, `ru-ngr`, `ru-psk`, `ru-sak`, `ru-yan`.

**Но ловит она только полную потерю.** Порог бинарный — слой либо есть, либо
нет; частично урезанный пак проходит, потому что уцелевших городов хватает на
весь обязательный набор. В той же сборке все 84 пака отчитались OK, хотя `ru-bel`
содержал 9% нод области, `ru-lip` и `ru-kgd` — 14%, `ru-cu` — 18%.

**Частичную потерю ловит проверка по городам** (`check_cities`, с 2026-09-02).
Она берёт точки слоя `place` с нижнего зума пака, отбрасывает чужие по
`polygons/<код>.geojson` (в пак затекают соседи: у `ru-ad` на z11 видно 379
названий, 119 из них за границей) и смотрит, есть ли у каждой оставшейся дороги
в её тайле на `maxzoom` или хотя бы в соседнем. Соседний тайл нужен не для
мягкости: у деревни на 30 дворов подъезд запросто лежит в соседней клетке — так
отсеялись все три срабатывания на честном корпусе (Сармантаевка, Шестаево,
Луньгинский Майдан), при том что потерю целого куска это не маскирует.
Проверено на заведомо битом паке: `ru-len`, обрезанный до восточной половины
области, даёт «21 НП без дорог», здоровый — тишину.

Цена: локальный прогон корпуса 1 мин 20 с вместо секунд, поэтому под
`--base-url` проверка по умолчанию выключена (сотни range-запросов на пак);
`--cities on|off` переключает вручную. Что она **не** видит: аккуратно вырезанный
кусок, где пропали и дороги, и подписи НП — точки-то она берёт из самого пака.

**Что уже пробовали в качестве проверки и что не работает** — чтобы не
изобретать заново:

- *Доля случайных точек внутри границы, для которых есть тайл на maxzoom.* Не
  различает сломанный пак и разреженный: сломанная Курганская — 9%, здоровая
  соседняя Тюменская — 8%. Planetiler не печёт тайл там, где в OSM ничего нет, а
  в тайге таких тайлов большинство.
- *Отношение числа тайлов z14 к числу z10* (плотность, не зависящая от площади
  субъекта). 28 у сломанной Курганской против 37 у худшей здоровой — разрыв
  слишком мал, чтобы ставить порог.

## `planetiler.yaml`

Две секции, приоритет **на уровне отдельного флага**: `countries > defaults`.
Файл не обязателен — без него сборка идёт с дефолтами planetiler.

```yaml
defaults:                  # глобальные значения
  languages: ru,en
  maxzoom: 14
  simplify_tolerance: 0.1

countries:                 # переопределение на страну, ключ = iso (ru, by, …)
  # ru:
  #   simplify_tolerance: 1.5
```

Правила:

- **Что сюда кладём.** Только «настроечные» флаги, которые имеет смысл менять на
  регион (`exclude_layers`, `simplify_tolerance`, `languages`, `maxzoom`, …).
  Структурные флаги, `--download` и `--threads` — в коде `build_pmtiles.py`.
- **Приоритет на уровне флага, не секции.** Страна, задавшая только
  `simplify_tolerance`, унаследует `exclude_layers` из defaults. Слияние —
  `{**defaults, **countries[iso]}`.
- **Переопределение заменяет значение целиком**: списки не сливаются.
- **Уровня субъекта нет.** planetiler запускается один раз на страну, паки
  режутся из готовой сборки, поэтому разные флаги у соседних субъектов
  физически невыразимы. До 2026-09-02 секция `subjects` здесь была — что в ней
  стояло и сколько это давало, см. git history.
- **Формат «значение → флаг».** Скаляр → `--имя=значение`; список →
  `--имя=a,b,c`; `true` → голый `--имя`, `false` → флаг не передаётся. Имя ключа
  = имя флага planetiler без ведущих `--`.
Почему такие дефолты:

- `languages: ru,en` — приложение двуязычное (см. [`lib/l10n/`](../../lib/l10n)),
  иначе схема тянет `name:*` на всех языках.
- `maxzoom: 14` — потолок детализации OpenMapTiles. У векторных тайлов зум
  сверху — это потолок, а не диапазон, который нужно печь целиком: рендерер сам
  оверзумит выше maxzoom, масштабируя последний тайл.
- `minzoom: 11` — пирамида начинается с 11, под нижнюю ступень лестницы зумов
  дэша (z11–20). Обзорные зумы ниже при активной навигации не нужны и стоят
  денег: z0–14 это 4.95 ГБ, z11–14 — 4.62 ГБ (−6.7%), z13–14 — 3.75 ГБ (−24.3%)
  (замер 2026-09-02, на 84 паках — числа сравнимы между собой, не с текущими).
  **Вниз рендер не достраивает**: ниже minzoom экран пустой, а не грубый,
  поэтому обзор маршрута целиком (он и на z11 не помещается: ~40×23 км на
  526×300) остаётся за онлайн-тайлами — см.
  [`docs/offline_mode_ru.md`](../../docs/offline_mode_ru.md), §8.
- `simplify_tolerance: 0.1` — дефолт planetiler, вынесен явно, чтобы его можно
  было переопределить. Учитывать, что флаг действует **только ниже maxzoom**
  (`PlanetilerConfig.tolerance(z)` при `z >= maxzoom` берёт
  `simplify_tolerance_at_max_zoom`), а `landcover`/`landuse`/`building` задают
  себе tolerance сами и на него не смотрят.

Какие переопределения стоят сейчас и почему — в комментариях самого
[`planetiler.yaml`](./planetiler.yaml); там же список того, что намеренно НЕ
отключают (`water`, `building`, `maxzoom`) и по какой причине.

## Что на выходе

### Иерархия `out/`

```
out/
  index.json
  ru/
    ru-mos-mow.pmtiles
    ru-len-spe.pmtiles
    ru-ad.pmtiles
    ...
  by/
    by.pmtiles
```

Подкаталог на страну, а не плоский список: как только включим ещё пару стран,
в одном каталоге окажется 90+ файлов. Плюс так проще частичная заливка — если
пересобрали Россию, трогать нужно только `ru/`.

### `index.json`

Один манифест на весь `out/`, сгруппированный по странам — телефон получает
готовую структуру «страна → список регионов», не собирая её у себя:

```json
{
  "version": 1,
  "generated_at": "2026-09-03T08:27:35Z",
  "file_count": 80,
  "total_size": 4449888181,
  "countries": [
    {
      "iso": "ru",
      "mode": "subjects",
      "regions": [
        {
          "code": "ru-mos-mow",
          "path": "ru/ru-mos-mow.pmtiles",
          "size": 168922023,
          "sha256": "3fb89e722699975fb4b33c764f8d4c568ff67a92ed05f969f12af89204cffb4a"
        }
      ]
    }
  ]
}
```

- `version` — версия схемы самого манифеста, чтобы менять формат, не ломая
  старых клиентов молча.
- `generated_at` — один UTC-таймстемп на файл: время сборки индекса, оно же
  дешёвая проверка «менялось ли вообще что-нибудь».
- `file_count` / `total_size` — агрегаты, чтобы UI показал «скачать всё — N
  файлов, X ГБ» без суммирования на телефоне.
- `code` — он же имя файла без расширения: второй идентификатор рядом с именем
  файла не заводим. **Кодом субъекта он быть не обязан:** `ru-len-spe` — два
  субъекта в одном паке.
- `sha256` — не ради криптостойкости, а чтобы не тащить в проект второй хеш:
  он есть из коробки и в Python (`hashlib`), и в Dart (`package:crypto`).
- `path` — относительно `out/`, не абсолютный URL: базовый хост клиент
  подставляет сам.
- **Намеренно нет `name`** — приложение двуязычное, а генератор тайлов не должен
  знать про локализацию. Отображаемое имя по `iso`/`code` — таблица на стороне
  приложения.

Как этим пользуется телефон:

1. Качает только `index.json` и сравнивает `generated_at` с сохранённым. Не
   изменился — всё свежее, дальше можно не ходить.
2. Изменился — по каждому установленному паку сравнивает `sha256` с сохранённым
   при установке. Разошёлся — качаем заново именно этот файл.
3. После закачки пересчитывает sha256 полученных байт и сверяет — это проверка
   целостности самой закачки.

Имейте в виду: planetiler пишет в метаданные тайлсета время сборки, поэтому
sha256 пересобранного файла отличается, даже если данные OSM не поменялись. При
еженедельной пересборке с нуля это и так означает переустановку паков.

## Регенерация и публикация

Конвейер гоняется целиком заново раз в неделю, с удалением `out/` перед
пересборкой: каждый файл собирается с нуля, инкрементальной пересборки нет и не
планируется. Поэтому не нужна и логика чистки «осиротевших» файлов от
выключенных или переименованных регионов — `out/` каждый раз пустой.

Пересобирать `full/<iso>.pmtiles` при этом нужно только если поменялся исходный
`.osm.pbf`: перерезать паки (другой буфер, перекачанная граница) можно поверх
существующей сборки страны за минуту.

**Публикация** — `upload.sh`: `yc storage s3 cp --recursive ./out s3://<бакет>/`.
Скрипт не в git и делает ровно одно копирование, без временного каталога и
атомарной подмены, поэтому у него два свойства, которые надо помнить:

- **Он ничего не удаляет.** Пак, выпавший из набора (субъект уехал в `merge` или
  `exclude`), остаётся на бакете навсегда. Клиенту он не виден — тот ходит только
  по `index.json`, — но место занимает; сносить руками.
- **`index.json` уезжает первым**, по алфавиту раньше `ru/`. Всё время заливки
  манифест обещает паки, которых ещё нет: на 4.45 ГБ это порядка получаса.
  Именно так корпус 2026-09-02 остался битым (см.
  [`spec/remote_map_server.md`](../../spec/remote_map_server.md)). Закрывается
  порядком: сначала `ru/`, потом манифест отдельной командой.

**Клиентская часть** (выбор паков пользователем, скачивание, лимит места) —
следующая итерация, когда будут реальные данные и станет виден их размер.

## Открытые вопросы

- **Абхазия** [DEFERRED] — нет своего ISO 3166-1 кода и Geofabrik-экстракта
  (территория внутри грузинского). Источник данных и границу нужно решить
  отдельно, прежде чем ставить `enabled: true`.
- **Украина** [DEFERRED] — в OSM есть альтернативные релации границы для части
  территории (Крым, зона конфликта). Какую использовать — решить до включения.
- **Источники (`source`) остальных стран** в `regions.yaml` живым запросом к
  Geofabrik не сверялись: проверить ссылку перед первым включением любой из них.
- **Субъекты без `ISO3166-2`** — сейчас молча выпадают из сборки (83 из 89).
  Если они нужны, потребуется ручная таблица сопоставления.
