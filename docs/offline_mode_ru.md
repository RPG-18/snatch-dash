# Оффлайн-режим: что сделано и что осталось

«Офлайн-режим» — это три независимых куска, и они в разном состоянии:

| | Что это | Состояние |
|---|---|---|
| **(A) Рендер карты на дэше** | картинка, которая уезжает на приборку | **сделано** — MapLibre Native offscreen поверх скачанных PMTiles |
| **(B) Построение маршрута** | пересчёт при отклонении, прокладка нового | **не сделано** — Yandex driving router по сети |
| **(C) Поиск места назначения** | подсказки на экране «Маршрут» | **не сделано** — Yandex Suggest по сети |

Документ начинался как обзор open-source вариантов для всех трёх. Раздел (A)
теперь описывает принятое решение и отсылает к спекам; разделы (B) и (C) —
по-прежнему аналитическая записка, не план внедрения.

**Важное следствие того, что сделано только (A):** карта на дэше работает без
сети, а навигация — нет. Поездка по уже построенному маршруту переживёт
отсутствие интернета; попытка проложить новый или пересчитать после отклонения
— нет.

---

## 1. Где мы сейчас

В проекте два **независимых** конвейера рендера карты:

1. **In-app карта** (`RouteScreen`, `RoutePreviewScreen`, `DashScreen`) —
   виджет `yandex_maps_mapkit`, поиск через Yandex Suggest HTTP API +
   `SearchManager`, маршруты через Yandex driving router
   (`lib/nav/router.dart`). Целиком онлайн, проприетарный SDK. Не затронут
   ничем из сделанного ниже.
2. **Нативный рендер на дэш** — MapLibre Native в offscreen-режиме поверх
   локальных `.pmtiles`, оверлеи (маршрут, стрелка райдера, пин, GPS-пилюля)
   поверх снапшота на `Canvas`. Работает без сети полностью, при условии что
   пак нужного региона скачан.

До сентября 2026 второй конвейер был растровым: свой `TileProvider` тянул
`.webp`-тайлы стиля MapTiler `streets-v2` через nginx-прокси с зашитым ключом,
складывал в LRU-кэш на 200 МБ и префетчил вокруг маршрута. Это был
*квази-офлайн*: без сети до выезда кэш пуст, покрытие ограничено окрестностью
маршрута. Отказались от MapTiler из-за лимитов на тарифах Free/Flex и стоимости
собственной инфраструктуры вроде OpenFreeMap.

## 2. (A) Рендер карты — решено и сделано

**MapLibre Native в offscreen-режиме поверх PMTiles, собранных своим
конвейером.**

Что где описано — здесь только суть, детали в спеках:

| Тема | Где |
|---|---|
| Как из пака получается кадр дэша: стиль, несколько источников, камера, лестница зумов, глифы, режимы отказа | [`spec/drawing_from_local_tiles.md`](../spec/drawing_from_local_tiles.md) |
| Формат корпуса, `index.json`, протокол скачивания и оптимистичная блокировка | [`spec/remote_map_server.md`](../spec/remote_map_server.md) |
| Экран управления паками | [`spec/offline_maps_screen.md`](../spec/offline_maps_screen.md) |
| Конвейер сборки паков | [`tools/planetiler`](../tools/planetiler) |

### Почему MapLibre, а не векторный рендер в Canvas

Рассматривались Mapsforge (векторный рендер прямо в `android.graphics.Canvas`),
VTM, `flutter_map` + `vector_map_tiles` и растровые MBTiles-паки под тогдашний
`TileProvider`. Первый вариант выглядел самым дешёвым архитектурно — тот же
примитив, которым был написан старый `MapRenderer`, никакого GL.

Решающим оказался не рендер, а **стиль**. У MapLibre он описывается JSON по
спецификации Mapbox Style, редактируется в [Maputnik](https://maplibre.org/maputnik/)
визуально, и за отправную точку берётся готовый открытый стиль под схему
OpenMapTiles (наши паки собраны именно по ней) — Positron для светлой темы,
Dark Matter для тёмной. Свой растеризатор пришлось бы дописывать каждый раз,
когда захочется поменять вид карты; здесь это правка JSON.

Плюс лицензия BSD-2-Clause против LGPLv3 у Mapsforge/VTM и живой проект с
релизами против community-масштаба `mapsforge_flutter`.

Цена зафиксирована честно: крупная нативная библиотека в APK (7.5 МиБ
`libmaplibre.so` на `armeabi-v7a`, 10.3 МиБ на `arm64-v8a`), GL-контекст в фоне
и readback кадра в `Bitmap`. Zero-copy «GPU → кодек» этим выбором **не**
открывается — разбор в [`spec/drawing_from_local_tiles.md`](../spec/drawing_from_local_tiles.md).

### Что показала первая поездка (2026-09-04)

Главная неизвестная — держит ли offscreen-рендер целевые 4 fps — снята: снапшот
стоит 42–52 мс медианы при бюджете 250 мс, запас тройной. Фактический интервал
между кадрами сошёлся с целевым, `late=0`.

Открытым остаётся отказ, которого не предполагал никто: первый снапшот каждой
сессии падает с `Could not read asset`, и до правки это заклинивало снапшоттер
на всю сессию. Механизм восстановления (пересборка снапшоттера) уже в коде,
сама причина — нет: имя недостающего ассета назовёт лог следующей поездки,
главный подозреваемый — непокрытый диапазон глифов.

### Чего это не даёт

- **Маршрутизация и поиск остались онлайн** — см. (B) и (C).
- **Обзор маршрута целиком офлайн не работает.** В паках `minzoom: 11`, и на
  этом зуме экран 526×300 показывает городскую агломерацию, но не поездку на
  300 км. Ниже рендер ничего не достраивает — будет пустой экран, а не грубая
  карта.
- **In-app карта осталась на Yandex MapKit.** Побочная выгода на будущее:
  MapLibre со своим стилем и паками применим и там — через `maplibre_gl`, уже
  без второго набора данных. Но это отдельная и заметно более крупная задача:
  она тянет за собой (C).

## 3. (B) Построение маршрута офлайн

Не сделано. Ниже — обзор кандидатов, актуальный на момент написания.

| Решение | Язык/embedding | Формат данных | Лицензия | Мобильный прецедент |
|---|---|---|---|---|
| **GraphHopper** | Java (JVM, embeddable) | Собственный граф, строится из `.osm.pbf` | Apache-2.0 | Есть демо-приложение под Android, но офлайн-режим на Android официально не поддерживается разработчиками («should still work», не более) |
| **Valhalla** | C++ (через NDK/FFI) | Тайловый граф (`.valhalla` тайлы) | MIT | Используется в Guru Maps, Stadia Maps mobile SDK — рабочий мобильный прецедент есть |
| **OSRM** | C++ (через NDK/FFI) | Contraction Hierarchies (`.osrm`-файлы) | BSD-2-Clause | Практически только серверный юзкейс, зрелого мобильного embedding-пути не сложилось |
| **BRouter** | Java (Android-native по задумке) | `.rd5` сегменты (компактные, по регионам) | MIT (по факту, «максимально пермиссивно») | Родом с Android — отдельное open-source приложение и плагин OsmAnd; на нём построен Kurviger (популярное мото-навигационное приложение) |
| Routino / itinero | C / .NET | свои форматы | GPLv2 / MIT | Нет живого мобильного прецедента — упомянуты для полноты, не рекомендуются |

### GraphHopper

- **Плюсы**: Apache-2.0 — самая permissive из «тяжёлых» лицензий здесь,
  специально выбрана авторами, чтобы можно было встраивать даже в закрытые
  продукты. Есть встроенный `motorcycle`-профиль из коробки (важно для
  мото-специфики проекта — веса дорог/поворотов можно настраивать под стиль
  езды). Java — тот же рантайм, что и остальной нативный код проекта
  (Kotlin/JVM), не нужен второй toolchain (NDK/C++), в отличие от
  Valhalla/OSRM.
- **Минусы**: разработчики прямо говорят, что офлайн-режим на Android
  официально не поддерживается — работает, но нужно самому решать проблемы
  вроде ограничений виртуальной памяти на телефоне и дробления графа на
  регионы (нет готового «tiled» механизма из коробки, как у Valhalla).
  Построение графа под регион размером с область — тяжёлый офлайн-препроцессинг
  (нужен сервер, не телефон), плюс сам граф ощутимо больше по объёму, чем
  аналогичное покрытие у BRouter.

### Valhalla

- **Плюсы**: тайловая, иерархическая структура графа спроектирована именно под
  мобильные/embedded ограничения по памяти (это явная цель дизайна) — лучше
  остальных тяжёлых движков подходит для смартфона. Реальный мобильный
  прецедент (Guru Maps, Stadia Maps SDK) — значит, интеграция в
  Android-приложение не гипотетическая, а проверенная в бою.
- **Минусы**: C++ — нужен NDK/FFI-мост, а не прямой Kotlin/JVM вызов (дороже в
  поддержке, чем GraphHopper/BRouter на JVM). Собственный формат тайлов и
  предобработка `.osm.pbf` → Valhalla-тайлы — отдельная инфраструктура, которую
  тоже надо развернуть и поддерживать.

### OSRM

- **Плюсы**: очень быстрый роутинг (Contraction Hierarchies), зрелый и широко
  используемый проект (де-факто эталон для серверного роутинга на OSM),
  permissive-лицензия.
- **Минусы**: спроектирован и живёт в основном как серверный движок — зрелого
  пути «встроить в Android-приложение офлайн» в экосистеме практически нет.
  Собирать и гонять C++ backend на телефоне без готовых мобильных биндингов —
  самый рискованный вариант из трёх «тяжёлых» движков.

### BRouter

- **Плюсы**: единственный из перечисленных, спроектированный **с нуля под
  Android/embedded** — сам по себе open-source Android-приложение и плагин
  OsmAnd, поэтому «встраивание в мобильное приложение» — штатный, а не
  экзотический сценарий. Данные по регионам компактные (`.rd5`-сегменты,
  единицы–десятки МБ на область) — тот же порядок, что у наших паков карты, а
  не на порядок больше. Собственный язык описания профилей (`.brf`) позволяет
  тонко управлять весами дорог — этим пользуется **Kurviger**, популярное
  мото-навигационное приложение, чтобы предпочитать извилистые дороги и
  избегать автомагистралей — прямое попадание в аудиторию проекта. Лицензия
  максимально пермиссивная.
- **Минусы**: меньше «промышленного» тюнинга производительности, чем у
  GraphHopper/Valhalla/OSRM на очень больших графах (страна+) — но для
  региональных паков это, вероятно, не критично. Меньше формальной документации
  как библиотеки (исторически распространяется как приложение/сервис, а не как
  аккуратно оформленный SDK) — интеграцию придётся собирать по примерам
  community.

**Предпочтение, если браться: BRouter** — по совокупности Android-native
дизайна, компактных региональных паков, permissive-лицензии и готовой
экосистемы мото-профилей. GraphHopper — запасной вариант, если понадобится
что-то более «энтерпрайзное»; Valhalla — если проект готов взять на себя
C++/NDK-мост.

**Отдельно про пересчёт маршрута.** Сейчас
[off-route reroute](../spec/route_restructuring.md) всегда бьёт в Yandex по
сети. Это самое болезненное место связки «карта офлайн, маршрут онлайн»:
райдер, свернувший не туда в зоне без покрытия, видит карту, но не получает
нового маршрута.

## 4. (C) Поиск места назначения офлайн

Не сделано, и это самый слабый по готовым решениям кусок — ничего не закрывает
задачу так же хорошо, как разделы (A) и (B).

| Решение | Суть | Годится ли для офлайн на телефоне |
|---|---|---|
| **Photon** (komoot) | Elasticsearch-based геокодер поверх OSM/Nominatim-данных | Нет — это сервер (Java + Elasticsearch), не embeddable на Android; самохостинг решает вопрос независимости от Yandex, но не вопрос офлайна с телефона |
| **Nominatim** | Классический geocoder OSM, PostgreSQL/PostGIS | Нет — тяжёлый серверный стек, не для мобильного embedding |
| **Mapsforge POI** (`mapsforge-poi`) | Компаньон-библиотека к Mapsforge: строит офлайн SQLite-индекс POI по названию/категории | Частично — закрывает поиск POI по названию/типу, но не полноценный free-text геокодинг адресов |
| Свой индекс: `osmium`/`pyosmium` → SQLite FTS5 | Кастомный офлайн-индекс имён/адресов из `.osm.pbf`-экстракта на регион | Да, но целиком собственный код — готовой переиспользуемой библиотеки нет; ровно так устроен офлайн-поиск в OsmAnd/Organic Maps (свой бинарный индекс), только там это тысячи строк C++/Java |

**Вывод**: если реально нужен офлайн-поиск — единственный реалистичный путь —
собрать лёгкий индекс самим (SQLite FTS5 поверх выгрузки POI+адресов из
региона) и паковать его вместе с паком карты. Данные для этого уже есть: тот же
`.osm.pbf`-экстракт, из которого конвейер режет тайлы.

## 5. Откуда берутся данные

Для (A) вопрос закрыт — [`tools/planetiler`](../tools/planetiler) собирает
корпус сам:

- **Экстракты OSM**: [Geofabrik](https://download.geofabrik.de/) — исходное
  сырьё, обновление ~ежедневно.
- **Границы субъектов**: Overpass, `fetch_boundaries.py`; по ним `cut_packs.py`
  режет экстракт с буфером 2 км за границей.
- **Генерация тайлов**: [Planetiler](https://github.com/onthegomap/planetiler)
  по схеме OpenMapTiles → PMTiles, зумы 11–14.
- **Раздача**: свой S3-бакет с `accept-ranges: bytes`, манифест `index.json`.

Для (B) и (C) данные брались бы из тех же экстрактов — граф строится
`brouter`/`graphhopper import`/`valhalla_build_tiles`, поисковый индекс —
`osmium` + SQLite FTS5. Отдельные шаги конвейера, но тот же источник, то есть
работа по (A) не одноразовая.

## 6. Риски и что учитывать

- **Атрибуция.** Переход на чистый OSM снял лицензионную зависимость от
  MapTiler, но добавил обязательную атрибуцию. На кадре дэша её нет намеренно
  (526×300 под круглым безелем), поэтому она держится целиком на карточке «О
  приложении» — см.
  [`ATTRIBUTION.md`](../packages/opendash_dash_engine/android/src/main/assets/ATTRIBUTION.md).
  Убрать оттуда строки нельзя, не вернув надписи на кадр.
- **Объём данных.** Корпус РФ — 4.45 ГБ на 80 паков, медиана 41 МБ, от 3.1 МБ
  (Ингушетия) до 356 МБ (Якутия). Скачивание обязательно и явно: без пака
  навигация на дэше заблокирована.
- **Актуальность.** OSM меняется постоянно; пересборка корпуса меняет `sha256`
  каждого пака даже без изменений в данных (в тайлсет попадает штамп сборки),
  поэтому «есть обновление» после пересборки показывается для всего сразу —
  см. `spec/remote_map_server.md`, «Проверка обновлений».
- **Два независимых рендер-конвейера — двойная работа.** In-app карта остаётся
  на Yandex MapKit, и полный переход на единый open-source стек потребовал бы
  переписать `RouteScreen`/`RoutePreviewScreen`/`DashScreen` вместе с заменой
  Yandex Suggest на (C).
