# Мультимедиа на приборке — автомат оригинального приложения

Что официальное приложение Royal Enfield показывает на дэше, когда на телефоне
играет музыка, и по каким правилам. Восстановлено из декомпиляции
(`Royal Enfield App 10.1.22`, 22.09.2026) — это описание **чужого** поведения,
эталон для сравнения, а не спецификация нашей реализации.

**На железе не проверялось ничего из этого.** Прошивка, против которой работал
оригинал, неизвестна; наша единственная проверенная — 11.63. Каждое
утверждение ниже прослеживается до конкретного метода в декомпиляции, но
«так в коде» и «так на приборке» — разные вещи.

Формат пакетов, таблица TLV и полная карта кодов джойстика —
[`docs/k1g_commands_RU.md`](../docs/k1g_commands_RU.md). Здесь только медиа и
только поведение.

## 1. Что сюда не относится

Полезнее начать с вычитания, потому что тут наша документация ошибалась.

Раз в секунду оригинал шлёт на дэш блок статуса телефона. В нём есть поля,
которые выглядят как медийные и таковыми не являются:

| TLV | Что на самом деле | Источник |
|---|---|---|
| `06 01` | есть ли сотовый сигнал (`01`/`00`) | `TelephonyManager.getAllCellInfo()`, уровень > 0 |
| `06 03` | включён ли GPS (`55`/`AA`) | `LocationManager.isProviderEnabled(GPS)` |
| `06 04` | **заряд батареи + 100** | `BatteryManager.BATTERY_PROPERTY_CAPACITY` |
| `06 0F` | заряжается ли телефон (`55`/`AA`) | `BATTERY_CHANGED`, статус `CHARGING`/`FULL` |

`06 04` — это батарея, а не громкость. Прежняя редакция
[`docs/k1g_commands_RU.md`](../docs/k1g_commands_RU.md) называла его громкостью
медиа и приводила как подтверждение расчёт «`0xA2` = 162 → громкость 62».
Арифметика верна, вывод нет: 62 — это процент заряда. `06 03` и `06 0F` там же
числились «булевыми флагами медиа» — они про GPS и зарядку.

Громкость на дэш тоже уходит, но другими TLV — см. §4.

## 2. Участники

| Роль | Оригинал | Наш аналог |
|---|---|---|
| Держатель гранта на уведомления | `NotificationService` — **пустой** `NotificationListenerService` | `OpenDashNotificationListener` |
| Владелец сессии и отправитель | `REForeGroundService` | `MediaInfoProvider` + `DashSession` |
| Интерфейс команд плеера | `igi` (`I`, `M`, `N`, `n`, `s`) | методы `MediaInfoProvider` |
| Нарезка обложки | `MetaDataUtils` (`nbg`) | нет |
| Диспетчер кнопок | `aaq.S()` → `s05` | `DashButtonController` (Dart) |

`NotificationService` не содержит ни одного метода. Он существует ровно затем,
чтобы у приложения был компонент, которому пользователь выдаёт доступ к
уведомлениям, — без этого `MediaSessionManager.getActiveSessions(component)`
кидает `SecurityException`. Тот же приём у нас.

## 3. Автомат

### 3.1 Состояния

```
НЕТ ДОСТУПА ──выдан доступ──▶ ИЩЕМ СЕССИЮ ──нашли──▶ ПРИВЯЗАНЫ
     ▲                             │  ▲                   │
     │                      не нашли│  │                  │ сессия сменилась
     └──────────── отозван ─────────┘  └──────────────────┘
```

- **НЕТ ДОСТУПА** — `wkh.u(this)` (список слушателей уведомлений) не содержит
  пакет приложения. Ничего не шлётся, ошибок не показывается.
- **ИЩЕМ СЕССИЮ** — `REForeGroundService.x()`. Берётся **нулевая** сессия из
  `getActiveSessions(NotificationService)`. Если список пуст → `05 17 AA`
  («медиа не активно») и выход.
- **ПРИВЯЗАНЫ** — `J()`: создаётся `MediaControllerCompat`, регистрируется
  колбэк, **сразу** уходит `05 17 55`, следом — карточка по текущим
  метаданным.

Переход «сессия сменилась» — `y()`: отписка, обнуление контроллера и токена,
затем снова `x()`. Дёргается через глобальный слушатель `erg.a()`, который
приложение зовёт из базовой Activity («Music event received from
REbaseActivity»); точное место, где он срабатывает, проследить по
обфусцированному коду не удалось.

`x()` вызывается ещё и на **каждый** `onStartCommand` сервиса — то есть
перепривязка происходит и при любом перезапуске переднего сервиса.

### 3.2 Метаданные

`REForeGroundService.A(MediaMetadataCompat)` — вся логика карточки:

```
onMetadataChanged
  └─ счётчик в колбэке: обрабатывается КАЖДЫЙ ВТОРОЙ вызов
       ├─ title, artist и album все null      → 05 17 AA, выход
       ├─ mediaId И title те же, что в прошлый
       │  раз                                  → выход, ничего не шлётся
       └─ иначе:
            05 0D  album \0 title \0 artist    (по 19 символов на поле)
            обложки нет   → 05 58 AA
            обложка есть  → 05 58 55, затем чанки 05 40
```

Два фильтра подряд — это не перестраховка. `onMetadataChanged` у многих
плееров срабатывает пачкой при смене трека (сначала приходит заголовок, потом
обложка, потом длительность), и без счётчика дэш получал бы карточку три раза
на один трек. Дедупликация по паре `mediaId` + `title` ловит уже другое:
повторную публикацию тех же метаданных при паузе/возобновлении.

Две ветки, до которых своим умом не дойти:

- `METADATA_KEY_ADVERTISEMENT != 0` → на дэш уходит альбом `"Advertisement"`,
  заголовок и исполнитель пустые. Плеер объявил рекламу — приборка это
  показывает;
- `IllegalStateException` при сборке пакета → фолбэк с заголовком
  `"NowPlaying"` и пустыми остальными полями. То есть при сбое лучше пустая
  карточка, чем никакой.

### 3.3 Воспроизведение

```
onPlaybackStateChanged
  05 17 55                       ← всегда, ПЕРЕД состоянием
  STATE_PLAYING (3) → 05 19 55
  STATE_PAUSED  (2) → 05 19 AA
  прочие состояния  → ничего, кроме 05 17 55
```

`05 17 55` шлётся безусловно на каждое изменение состояния, включая буферизацию
и остановку. Приборка узнаёт «медиа есть» заново при каждом чихе плеера — это
дешевле, чем отслеживать, знает ли она об этом.

Состояния кроме `PLAYING` и `PAUSED` (`STOPPED`, `BUFFERING`, `ERROR`)
индикатор не трогают: он остаётся в том виде, в каком был.

## 4. TLV медиа

| TLV | Значение | Когда |
|---|---|---|
| `05 0D` | `album \0 title \0 artist`, по 19 символов | смена трека |
| `05 17` | `55` медиа активно · `AA` не активно | привязка, смена состояния, потеря сессии |
| `05 19` | `55` играет · `AA` пауза | смена состояния |
| `05 58` | `55` дальше обложка · `AA` обложки нет | сразу после `05 0D` |
| `05 40` | чанк JPEG обложки | после `05 58 55` |
| `05 4C` | громкость `STREAM_MUSIC`, 11 ступеней | 1 Гц, в блоке статуса |
| `05 1B` | громкость `STREAM_VOICE_CALL`, 11 ступеней | 1 Гц, в блоке статуса |

Громкости кодируются одинаково: `0x10` — тишина, `0x11`…`0x1A` — десять
ступеней. Шаг считается как `(max - min) / 10` и текущее значение раскладывается
по корзинам; это не проценты и не абсолютное значение стрима.

`05 0D`, `05 40` и `05 22` (карточка звонка) собираются в коде побайтово, без
строковых констант, поэтому их нет в таблице констант `hbg` — и, соответственно,
в таблицах `docs/k1g_commands*.md`. Об этом там есть оговорка в «Покрытии».

## 5. Обложка альбома

Единственный TLV в протоколе, у которого внутри значения своя служебная
разметка. Сборка — `MetaDataUtils` (`nbg`): `c()` режет, `a()` делает первый
чанк, `e()` — остальные.

Подготовка: `ThumbnailUtils.extractThumbnail(art, 75, 75)`, затем
`Bitmap.createScaledBitmap(…, 75, 75)` и `JPEG quality 50`.

```
первый чанк:   05 40 | len = payload+3 | 00  | size_hi size_lo | payload…
последующие:   05 40 | len = payload+1 | idx | payload…
последний:     05 40 | len = payload+1 | FF  | payload…
```

- `size` — полный размер JPEG, big-endian u16, **только в первом чанке**;
- `idx` — номер чанка начиная с 1, `FF` вместо номера помечает последний;
- размер чанка 1000 байт, между пакетами `Thread.sleep(10)`;
- если картинка влезает в один чанк, вторым пакетом всё равно уходит пустой
  терминатор: `len = 1`, `idx = FF`, ноль байт нагрузки.

75×75 при quality 50 — это единицы килобайт, то есть обычно 2-5 чанков и
20-50 мс на передачу. Это ощутимо на фоне секундного такта, и `sleep(10)` в
отправляющем потоке — причина, по которой переносить эту схему дословно в наш
кадровый цикл нельзя.

Разметку не смог разобрать [NorthStar](https://github.com/OpenMotoDash/NorthStar):
у него в `DashCommands.albumArtFrames` стоит пометка «fragment sub-framing
unconfirmed… the 2-byte intra-value prefix we saw isn't decoded yet», и функция
намеренно ниоткуда не вызывается. Префикс не двухбайтовый — три байта у первого
чанка и один у остальных, из дампа это неразличимо.

## 6. Управление с джойстика

Медиа-коды из диспетчера `aaq.S()`; полная карта всех 19 —
в [`docs/k1g_commands_RU.md`](../docs/k1g_commands_RU.md), «Кнопки `09 00`».

| код | действие | как сделано |
|---|---|---|
| `05` | play/pause | `igi.I()` — читает `PlaybackState`, шлёт `pause()` или `play()` |
| `06` | громкость медиа + | `igi.N()` → `MediaControllerCompat.adjustVolume(+1)` |
| `07` | громкость медиа − | `igi.M()` → `adjustVolume(-1)` |
| `09` | следующий трек | `igi.s()` → `skipToNext()` |
| `0A` | предыдущий трек | `igi.n()` → `skipToPrevious()` |
| `08` | mute вкл/выкл | `AudioManager.adjustStreamVolume(STREAM_MUSIC, ±100)` |

Все пять медиа-веток начинаются с проверки «контроллер привязан?». При `null`
не происходит **ничего** — ни действия, ни эха `06 80`. С точки зрения дэша
молчание на нажатие означает и «такой кнопки нет», и «музыка не играет»; разделить
их нельзя.

Отдельно стоит `08`: он трогает `AudioManager` напрямую, а не сессию, и потому
работает даже без привязанного контроллера — и эхо шлёт всегда.

Код `18` подписан в отладочной строке как «start music», но вызывает `m9()`,
который отправляет **счётчик пропущенных звонков** (`06 0A`) и музыку не
запускает. Либо строка устарела, либо метод. Эха у этого кода тоже нет.

### 6.1 Громкость подтверждения не получает

Зум на каждое нажатие отвечает дэшу немедленно: эхо `06 80`, а следом `06 0C` с
новым состоянием пределов. **Громкость устроена иначе — эхо и всё.**

| код | что делает | что отправляет |
|---|---|---|
| `03` | `adjustStreamVolume(STREAM_VOICE_CALL, +1, FLAG_PLAY_SOUND)` | `06 80 03` |
| `04` | то же, `-1` | `06 80 04` |
| `06` | `MediaControllerCompat.adjustVolume(+1)` | `06 80 06` |
| `07` | то же, `-1` | `06 80 07` |
| `08` | `adjustStreamVolume(STREAM_MUSIC, ±100)` | `06 80 08` |

Ни один из пяти обработчиков не отправляет `05 4C` или `05 1B`. Проверено по
всем одиннадцати константам каждой шкалы (`n1`…`x1` и `y1`…`I1`): они
встречаются ровно в двух местах, и оба — тела таймеров (`TimerTask d` и мёртвый
`TimerTask e`), ни одного вызова из обработчика кнопки. Обходного пути тоже нет:
во всём пакете `com/royalenfield/` нет ни `ContentObserver` на
`Settings.System.VOLUME_*`, ни приёмника `VOLUME_CHANGED_ACTION` — громкость
исключительно опрашивается.

Отсюда три следствия:

- **до секунды задержки** между нажатием и движением шкалы на приборке;
- **вне режима `INFOTAINMENT` дэш о новой громкости не узнаёт вовсе** — блок
  статуса не тикает, а эхо несёт только код кнопки;
- мгновенная обратная связь есть, но у телефона, а не у дэша: флаг
  `FLAG_PLAY_SOUND` даёт системный «бип». У mute флаг `0`, он молчит.

Почему так, а не как у зума, из кода не видно. Разница в том, что состояние
камеры существует только в приложении, а громкость — свойство системы, которое
всё равно приходится опрашивать; но объяснение это, а не оправдание задержки.

Для порта это упрощает работу: обе шкалы можно считать прямо в хартбите из
`AudioManager` на каждом такте, без отдельного пути «кнопка → пакет».

## 7. Каденции

| Что | Период | Условие |
|---|---|---|
| Блок статуса (включая обе громкости) | 1 Гц | режим дэша `INFOTAINMENT` |
| Карточка `05 0D` | по событию | смена трека, с дедупликацией |
| `05 17` / `05 19` | по событию | смена состояния плеера |
| Обложка | по событию | вместе с карточкой, если есть |

Карточка **не** повторяется в 1 Гц. Оригинал отправляет её один раз на трек и
полагается на то, что дэш её помнит.

Громкость, наоборот, живёт только в опросе: изменение с джойстика не порождает
пакета со значением, дэш узнаёт новый уровень на следующем такте (§6.1).

Блок статуса поднимается только в режиме `INFOTAINMENT` (`t9k.b`), то есть
медиа на приборке — часть этого режима, а не отдельная функция. В коде есть
второй, почти такой же 1 Гц таймер (`P()` → задача `e`), который не вызывается
ниоткуда; считать его действующим нельзя.

## 8. Что из этого есть у нас

| | оригинал | snatch-dash |
|---|---|---|
| `05 0D` | по событию, дедупликация | **1 Гц безусловно** |
| порядок полей | `album, title, artist` | `title, album, artist` |
| длина поля | 19 | 20 |
| `05 17` | да | только `AA` в стартовом бёрсте, без пояснения |
| `05 19` | да | нет |
| `05 58` / `05 40` | да | нет |
| `05 4C` / `05 1B` | живые значения, 1 Гц | захваченные константы `13` и `19` |
| джойстик: play/pause, громкость | да | нет (эти коды у нас значат другое) |
| джойстик: next/prev | да | да |

Наша медиа-часть — дословный потомок NorthStar: совпадают имена файлов, состав
модели и оба реализованных TLV. Оттуда же унаследованы порядок полей, лимит 20
и неиспользуемое поле `NowPlaying.art`: обложка вычитывается в память и никуда
не отправляется.

Практическое следствие для райдера: у нас приборка не узнаёт ни о паузе, ни о
том, что музыка кончилась. `05 0D` продолжает идти раз в секунду с последним
треком — до конца сессии.

## 9. Открытые вопросы

Всё это решается железом, а не чтением, и вынесено в
[`docs/ON_HARDWARE_VERIFICATION_RU.md`](../docs/ON_HARDWARE_VERIFICATION_RU.md), §6.

- **Порядок полей в `05 0D`.** Оригинал и NorthStar расходятся. Проверяется
  треком, у которого название заведомо не совпадает с альбомом.
- **19 или 20 символов.** Разница ровно в единицу подозрительно похожа на
  «19 символов + завершающий ноль», то есть возможно, что правы оба.
- **Держит ли прошивка 11.63 карточку без повторов.** Если нет, дедупликация
  оригинала на нашей прошивке даст исчезающую карточку, и 1 Гц окажется не
  ошибкой, а обходом.
- **Рисует ли 11.63 обложку вообще.** Формат разобран, но отправлять его в
  прошивку, которая его игнорирует, — потраченный такт и `sleep` в живом потоке.
- **Что на самом деле делает код `18`.**
