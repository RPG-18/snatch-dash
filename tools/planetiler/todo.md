# Отложенное по конвейеру тайлов

Что решено сделать, но не сделано. Одна запись — одна задача: зачем, что уже
выяснено (чтобы не перемерять) и с чего начинать. Сделанное отсюда убирать, а
не помечать галочкой — что и когда поменялось, видно по git history, а не
здесь.

Клиентская часть (стиль, глифы, скачивание паков на телефон) живёт отдельно —
см. [`docs/offline_mode_ru.md`](../../docs/offline_mode_ru.md), §8, и
[`spec/drawing_from_local_tiles.md`](../../spec/drawing_from_local_tiles.md).

## 1. Метрики покрытия — не опровергнуты, а не проверены

Первые две попытки автоматической проверки были отброшены на ложной посылке:
сравнивались Курганская область (9% покрытия) и «здоровая» Тюменская (8%), а
Тюменская, как выяснилось позже, была сломана точно так же (Тюмень на месте,
Тобольска, Ишима и Ялуторовска нет вовсе). То же с отношением числа тайлов
z14 к z10 (28 против 37) — «здоровые» паки в том замере по городам никто не
проверял. Этот замер вдобавок больше не воспроизвести: z10 в паках нет с
`minzoom: 11`, считать пришлось бы z14/z11.

Отдельной работы это не требует: проверка по городам (`check_cities` в
`validate_packs.py`, сделана 2026-09-02) сильнее и порога не просит. Запись нужна на случай, если к метрикам покрытия вернутся —
калибровать заново, на паках, прошедших проверку по городам.

## 2. Помнить при следующей минимизации: соседние паки видны одновременно

На дэше одновременно активны несколько паков (город + окружающая область;
Чукотка вообще собрана двумя файлами). Поэтому субъект-специфичные
`exclude_layers` дают видимый шов на границе: в сборке 2026-08-31 `ru-len` был
без `landcover`, а `ru-spe` с ним, и фоновая заливка леса появлялась и
исчезала при въезде в город.

Сейчас проблемы нет, и вернуться она может только вместе со сменой схемы
сборки: с 2026-09-02 planetiler запускается один раз на страну, так что разные
`exclude_layers` у соседних субъектов физически невыразимы. Запись оставлена на
случай, если кто-то захочет собирать отдельные субъекты мимо общей схемы
(например, город с `maxzoom: 15`) — тогда шов вернётся.

**Как делают другие.** [OsmAnd](https://osmand.net/blog/fast-routing/)
намеренно включает в регион кластеры, вылезающие за его границу, чтобы маршрут
бесшовно считался через границу скачанных файлов. Мы держим активными несколько
паков одновременно, поэтому для рендера такое перекрытие не обязательно — но
райдеру с одним скачанным паком оно нужно, поэтому с 2026-09-02 паки режутся с
буфером 2 км (`cut_packs.py`, `--buffer-km`), что стоит по корпусу +3.4%.

Для тайлов перекрытие теперь есть; **если дойдёт до офлайн-маршрутизации**
(§3 [`docs/offline_mode_ru.md`](../../docs/offline_mode_ru.md)), её данные так
резать нельзя: маршрут будет обрываться на границе субъекта. Обрезка — решение
для тайлов, а не для графа.

## 3. Почему bbox субъекта НЕ кладём в `index.json`

Такая задача тут стояла — снята 2026-09-02, чтобы её не завели заново.

Потребителей у поля оказалось ноль:

- **Экран загрузки.** Райдер выбирает «Ленинградскую область» по названию: он
  знает, где он и куда едет. Координаты ему для этого не нужны.
- **Какие паки держать активными.** Здесь bbox нужен, но брать его из манифеста
  незачем: речь только про уже скачанные паки, а у каждого в заголовке PMTiles
  с 2026-09-02 лежит честный bbox региона (`pmtiles extract --region` пишет его
  из полигона; у `ru-len` это 26.4–35.7° в. д. вместо прежних 13.6–37.9°).
  Прочитать 127 байт заголовка локального файла дешевле, чем тащить поле через
  манифест.

Единственный сценарий, где поле понадобилось бы, — подсказка про **не скачанный**
пак («впереди Тверская область, скачать?»). Такой функции в спеках нет; появится
— задача вернётся, и тогда считать bbox надо из границы `polygons/<код>.osm`,
а не из заголовка (там граница плюс буфер 2 км). Отдельно помнить про Чукотку:
её bbox через антимеридиан одним прямоугольником не выражается — либо два, либо
конвенция [RFC 7946 §5.2](https://datatracker.ietf.org/doc/html/rfc7946#section-5.2)
«запад > восток».
