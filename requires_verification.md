# Требует проверки другой моделью

Список потенциальных ошибок, найденных при ручном разборе кода (`lib/` +
`packages/opendash_dash_engine`). Каждый пункт самодостаточен: содержит
утверждение, ссылку на точные строки, фрагмент кода, обоснование и конкретный
шаг проверки. Цель — чтобы вторая модель могла **независимо** подтвердить или
опровергнуть каждый вывод, читая только код, без контекста этого обсуждения.

Соглашения:
- Номера строк соответствуют состоянию файлов на ветке `planetiler-offline-tiles`.
- «Требует проверки» не означает «точно ошибка» — это гипотезы для верификации.
- `flutter analyze` в окружении автора недоступен (нет Flutter SDK), поэтому
  компиляционные гипотезы (п. 1) помечены как требующие машинной проверки.

## 1. `main.dart` — пропущены `break` в switch по жизненному циклу — ОПРОВЕРГНУТО

**Серьёзность:** критическая (ошибка компиляции или неверное поведение).

**Файл:** `lib/main.dart`, строки 44–58.

**Код:**
```dart
class _MapkitLifecycleObserver extends WidgetsBindingObserver {
  @override
  void didChangeAppLifecycleState(AppLifecycleState state) {
    switch (state) {
      case AppLifecycleState.resumed:
        mapkit.onStart();
      case AppLifecycleState.paused:
        mapkit.onStop();
      case AppLifecycleState.inactive:
      case AppLifecycleState.detached:
      case AppLifecycleState.hidden:
        break;
    }
  }
}
```

**Утверждение (исходное, ложное):** после `mapkit.onStart()` (строка 49) и
`mapkit.onStop()` (строка 51) нет `break`. В Dart непустой `case` обязан
завершаться `break`/`return`/`throw`/`continue`; иначе анализатор выдаёт
«The 'case' should not complete normally» (ошибка компиляции).

**Почему это неверно:** начиная с Dart 3 (enhanced switch statements),
компилятор **больше не требует** явного `break` и **не допускает implicit
fallthrough** для непустых `case`-тел — каждое непустое тело автоматически
завершается неявным `break` после выполнения. Явный fallthrough в новом Dart
возможен только через `continue caseLabel;`. Старое поведение C-подобных
языков (и старых версий Dart, где это было ошибкой компиляции) здесь не
применимо.

**Проверено практически, а не только по памяти о спеке:**
1. `dart analyze lib/main.dart` (Dart SDK 3.12.2, реально установлен в
   `~/develop/flutter`) → `No issues found!`.
2. Минимальный воспроизводящий пример с точно такой же структурой
   (`case A: print('start'); case B: print('stop');`), скомпилирован и
   запущен:
   ```
   f(S.resumed) → печатает только "start" (НЕ переходит на case B)
   f(S.paused)  → печатает только "stop"
   ```
   Fallthrough не происходит ни на уровне компиляции, ни на уровне
   рантайм-семантики.

**Вывод:** код в `main.dart:44-58` корректен как есть, компилируется без
ошибок и не менеджит переходов `resumed → onStart()+onStop()`. Правка не
требуется.

## 2. Fallback-глиф манёвра `0x0B` вместо нейтрального `0x09` — ПОДТВЕРЖДЕНО

**Серьёзность:** средняя (неверный глиф в критичный момент навигации).

**Файлы (места, где зашито `0x0B`):**
- `lib/nav/nav_loop.dart:96` — `maneuver: progress.nextManeuver?.dashCode ?? 0x0B`
- `packages/opendash_dash_engine/lib/opendash_dash_engine.dart:44` — `int maneuver = 0x0B`
- `packages/opendash_dash_engine/lib/opendash_dash_engine_platform_interface.dart:51` — `int maneuver = 0x0B`
- `packages/opendash_dash_engine/lib/opendash_dash_engine_method_channel.dart:60` — `int maneuver = 0x0B`
- `packages/opendash_dash_engine/android/src/main/kotlin/com/opendash/opendash_dash_engine/OpendashDashEnginePlugin.kt:121` — `maneuver = call.argument<Int>("maneuver") ?: 0x0B`

Проверено построчно — все пять мест действительно используют `0x0B` как
default/fallback значение. Также обнаружено дополнительное место с тем же
эффектом: `NavLoop.start()` (`nav_loop.dart:54-60`) вызывает `setNavState(...)`
вовсе без параметра `maneuver`, то есть тоже попадает на дефолт `0x0B` в
момент старта маршрута — до первого тика.

**Свидетельство, что нейтральный глиф — `0x09`, а не `0x0B`:** подтверждено
чтением `lib/nav/route.dart:49-54,136-143` (fallback `0x09`) и
`DashCommands.kt:280-291` (`NAV_MANEUVER_STRAIGHT = 0x09`, явный комментарий
о том, что `0x0B` — унаследованная от `open-dash` ошибочная догадка,
опровергнутая на реальном железе).

**Проверка цепочки:** `activeNavPacket` (`DashCommands.kt:316-317`)
дефолтится в `NAV_MANEUVER_STRAIGHT`, но фактический вызов идёт через
`DashEngineController` с явным `maneuver`-значением, пришедшим по method
channel от Dart — а там дефолт уже `0x0B`, перекрывающий корректный нативный
дефолт. Цепочка подтверждена.

**Предлагаемое исправление:** заменить все пять (фактически шесть, считая
неявный вызов в `start()`) `0x0B` на `0x09`.

## 3. `publishState` затирает GPS/nav-состояние на каждом «не-tick» событии — ПОДТВЕРЖДЕНО

**Серьёзность:** средняя (мигание маркера райдера / флагов на экране Dash,
отсутствие GPS-статуса во время подключения).

Проверено: `DashEngineController.kt:783-823` — сигнатура `publishState` с
nullable-параметрами по умолчанию `null`, подтверждена. Проверены все 9
вызовов `publishState(` в файле (строки 210, 233, 261, 305, 338, 351, 373,
380, 646) — реальные GPS/nav значения передаёт только вызов на строке 646
(внутри `tick()`), остальные 8 вызовов либо без аргументов, либо только с
`errorMessage`/`explicitDisconnect`, оставляя GPS-поля `null`.

Проверено также, что `tick()` вызывается только из `streamJob`
(`while (isActive && session.state.value == DashState.STREAMING) { tick() }`,
строки 574-576) — то есть только во время `STREAMING`, не во время
`CONNECTING`/`AUTHENTICATING`/`READY`.

**Файл (Dart):** `lib/state/dash_engine_state.dart` — подтверждено, что
`fromMap` (80-101) превращает отсутствующие ключи в `false`/`null`
(`?? false` для булевых, голый `as num?` для nullable-double), и что
`DashEngineStateNotifier.build()` (120-129) **полностью заменяет** `state`
на каждый raw-эвент через `ref.listen`, без merge с предыдущим значением.

**Вывод:** подтверждено дословно — любое не-`tick`-событие (смена
WiFi-статуса, session-статуса, media/call-forwarding, `setDestination`/
`clearDestination`, `disconnect`) обнуляет `hasGps`/`riderLat`/`riderLng`/
`riderBearing`/`remainingKm`/`offRoute`/`gpsLost`/`gpsWeak` в Dart-состоянии
до следующего `tick()`, то есть до входа в `STREAMING`.

**Предлагаемое исправление:** как в оригинале — читать текущие значения из
`locationTracker`/собственных полей вместо nullable-параметров, либо
на Dart-стороне мёржить только присутствующие в map ключи вместо полной
замены state.

**Уточнение 3-й проверки (область поражения — проверены потребители):**
вывод верен, но полезно знать, кого именно задевает:
- **`NavLoop` НЕ задет** — `_onEngineEvent` (`nav_loop.dart:73-80`) гвардит
  `if (lat != null && lng != null)`, то есть хранит last-known позицию сам и
  игнорирует обнулённые события. Логика навигации/реройта не страдает.
- **Экран Dash задет напрямую** — `dash_screen.dart:47,49,59,61,67,70,76`
  читает `engine.riderLat/riderBearing/gpsLost/gpsWeak/remainingKm`. Значит
  видимый эффект: маркер райдера прыгает/пропадает, чипы «GPS потерян/слаб»
  мигают, чип остатка дистанции исчезает — ровно то «мигание», что заявлено.

То есть баг косметический по последствиям (навигация корректна), но
проявляется именно там, где заявлено.

## 4. Гонка в `DashSession.disconnect()` — `setState(READY)` после разборки — ПОДТВЕРЖДЕНО

**Серьёзность:** средняя (потенциальный запуск стрима на закрытом сокете).

Проверено построчно:
- `disconnect()` (`DashSession.kt:195-210`): `sessionJob?.cancel()` вызывается
  первым (не `cancelAndJoin()` — не блокирующий, не ждёт завершения), затем
  закрывается сокет и `setState(IDLE)`.
- `runSession` (`DashSession.kt:214-266`) действительно заканчивается
  `enterNavMode(sock); setState(DashState.READY)` (строки 259-260).
- `enterNavMode` (`DashSession.kt:273-286`): последняя suspend-точка —
  `delay(40)` на строке 283. После неё — `sock.send(...)` (строка 284) и
  `DebugLog.i` (285), обе синхронны.
- Проверено определение `DashSocket.send` — `fun send(data: ByteArray)`,
  **не** `suspend fun`, то есть действительно нет точки, где кооперативная
  отмена могла бы прерваться между `delay(40)` и `setState(READY)`.
- Проверено, что `sessionWatchJob` в `DashEngineController` (`:264`) реагирует
  на `DashState.READY` вызовом `startStream()`, и что `startStreaming()`
  (`DashSession.kt:164-165`) гвардится только `if (_state.value != READY) return`
  — то есть не проверяет, был ли этот READY выставлен уже после разборки.

**Вывод:** гонка реальна и воспроизводима по логике кода: если
`disconnect()` вызывает `sessionJob.cancel()` именно в узком окне между
`delay(40)` (283) и `setState(READY)` (260), `runSession` всё равно дойдёт до
`setState(READY)` на уже закрытом/обнулённом сокете.

### ⚠️ Коррекция 3-й проверки: путь и последствие описаны неверно

Сама гонка (окно между 283 и 260) подтверждается — но **механизм вреда,
описанный выше, по указанному пути невозможен**, а реальное последствие
серьёзнее.

**1. Пользовательский disconnect НЕ приводит к заявленному вреду.**
`DashEngineController.disconnect()` (`:288-306`) отменяет `sessionWatchJob`
**до** вызова `session.disconnect()`:
```kotlin
streamJob?.cancel(); streamJob = null
sessionWatchJob?.cancel(); sessionWatchJob = null   // ← отменён ПЕРВЫМ
wifiWatchJob?.cancel(); wifiWatchJob = null
stopMediaForwarding()
session.disconnect()                                 // ← и только теперь
```
К моменту гоночного `setState(READY)` коллектор уже мёртв и READY никто не
увидит. Ссылка на `DashEngineController.kt:264` как на доказательство вреда
некорректна для этого пути.

**2. Реально достижимый путь — потеря WiFi, а не действие райдера.**
`session.disconnect()` вызывается ещё и из `wifiWatchJob`
(`DashEngineController.kt:247`) при пропадании сети — и вот там
`sessionWatchJob` **жив**. Это единственный путь, где гонка что-то ломает.

**3. Последствие — не «стрим в закрытый сокет», а заклинивание сессии.**
Отправка в мёртвый сокет сама по себе безвредна (`socket?.send(...)` —
null-safe no-op, ошибки в `DashSocket.send` глотаются). Ломается другое:
- `sessionWatchJob` на READY вызывает `startStream()` → `startStreaming()`
  проходит гард и делает `setState(STREAMING)`;
- `st == STREAMING` → `cancelGiveupTimer()` (`:262`) — **обезвреживается
  сторожевой таймер**, который должен был сдаться через `RECONNECT_GIVEUP_MS`;
- когда WiFi возвращается, `wifiWatchJob` вызывает `session.connect(...)`, а
  тот молча выходит на гарде `if (_state.value != IDLE && != ERROR) return`
  (`DashSession.kt:159`) — состояние-то `STREAMING`.

Итог: после неудачно совпавшей потери WiFi сессия **навсегда зависает в
фиктивном STREAMING** — переподключение молча отклоняется, сторожевой таймер
снят, автоматического выхода нет. Это уже не «потенциальный запуск стрима на
закрытом сокете» (низкий вред), а невосстановимая потеря дэша на всю поездку
до ручного disconnect. **Серьёзность: средняя → высокая.**

**Предлагаемое исправление:** перед `setState(DashState.READY)` добавить
`ensureActive()` (бросит `CancellationException`, если job уже отменён) или
явную проверку `socket != null`. Дополнительно стоит закрыть класс проблемы:
гард в `startStreaming()` должен проверять и живой сокет, а не только
`_state == READY`.

## 5. FU-A-фрагментация применяется к связке SPS+PPS+IDR как к одному NAL — ПОДТВЕРЖДЕНО

**Серьёзность:** средняя (латентная — порча видео при IDR > MTU).

Проверено построчно:
- `NalProcessor.emitIdr` (`NalProcessor.kt:57-71`) действительно склеивает
  `sps + START_CODE_4 + pps + START_CODE_4 + idr` в **один** `ByteArray` и
  передаёт его **одним** вызовом `onNal(nal, true)`.
- `RtpPacketizer.packetize` (`RtpPacketizer.kt:38-45`) выбирает `fuA` по
  суммарному размеру этого бандла (`nal.size > MAX_PAYLOAD`, `MAX_PAYLOAD =
  1380`), не различая, что внутри несколько NAL-юнитов.
- `fuA` (`RtpPacketizer.kt:47-69`) берёт `nalType` из `nal[0]` — первого
  байта бандла, то есть байта SPS (тип 7) — и фрагментирует весь бандл как
  один NAL типа 7 согласно RFC 6184 FU-A.

**Вывод:** логическая ошибка подтверждена — при превышении бандлом
`MAX_PAYLOAD` получится протокольно невалидный H.264/RTP поток (множество
NAL-юнитов, замаскированных под фрагменты одного SPS).

### 🔴 Коррекция 3-й проверки: это не «латентная» ошибка — она срабатывает всегда

2-я проверка оставила открытым вопрос «насколько часто это реально
случается». Вопрос закрывается арифметикой по фактическому конфигу кодека
(`DashEncoder.kt:30-48`), и ответ — **на каждом IDR, то есть раз в секунду
на протяжении всего стрима**:

| Параметр | Значение |
|---|---|
| `WIDTH × HEIGHT` | 526 × 300 |
| `FPS` | 4 |
| `BITRATE` | 200 000 бит/с |
| `KEY_I_FRAME_INTERVAL` | **1** (IDR каждую секунду) |
| `MAX_PAYLOAD` | 1380 байт |

Бюджет одной секунды — 200 000 бит = **25 000 байт**, и при IDR раз в
секунду ключевой кадр забирает основную его часть. Даже при крайне
консервативной оценке IDR в 2 000 байт бандл `SPS + 4 + PPS + 4 + IDR`
кратно превышает 1380. Порог не «может быть превышен» — он не может быть
не превышен.

**Что получает дэш при реассемблировании.** `fuA` восстанавливает ровно один
NAL: заголовочный байт из `fuInd`/`fuHeader` (тип **7**, SPS) + всё
остальное как payload. То есть дэшу приходит «SPS», внутри которого после
RBSP лежит мусор — старт-код, PPS, старт-код и весь IDR-слайс. Декодер,
терпимый к хвостовым байтам после RBSP, **разберёт SPS и откроет декодер**
(размеры кадра он узнал), но **PPS и IDR-слайс как отдельные NAL не придут
никогда** → декодировать картинку не из чего.

**Это дословно совпадает с задокументированным симптомом на живом железе** —
`DashSession.kt`, доктаг `enterIdleProjectionMode`, попытка 2 из раздела
KNOWN BROKEN: «Decoder opened, but the dash rendered ONLY its route-card
chrome (title/glyph/distance bubble) full-screen on a blank background —
video plane never became visible». Ровно то, что даёт «SPS есть, PPS/IDR
нет». Симптом объяснялся режимом chrome и PTS-таймстемпами (см. доктаг
`RtpPacketizer.packetize` про полевую сессию 2026-08-29), после чего было
проведено несколько раундов правок на железе — но обе гипотезы не трогали
пакетизацию, а этот дефект её ломает независимо от них.

**Вывод:** п. 5 — не «средняя, латентная», а наиболее вероятная **корневая
причина главного нерешённого бага проекта** (видео не появляется на дэше).
Серьёзность: **средняя → критическая**, и чинить его стоит раньше остальных.

**Как подтвердить за одну сессию, без гаданий на железе:** `NalProcessor.kt:69`
уже логирует размер бандла для первых трёх IDR —
`emit IDR #N (${nal.size}B bundled)`. Одного `adb logcat -s NalProcessor`
достаточно: если число заметно больше 1380 (а оно будет), путь `fuA`
подтверждён фактическими данными.

**Предлагаемое исправление:** отправлять SPS и PPS отдельными маленькими
пакетами (они гарантированно < MTU и фрагментации не требуют) и
фрагментировать только сам IDR-NAL. Заодно имеет смысл сделать
`packetize` принимающим список NAL, чтобы «бандл» в принципе не мог
попасть во фрагментатор как единица.

## 6. `DashAuth.buildKeyPacket` — SSID > 85 байт роняет приложение — ПОДТВЕРЖДЕНО (и достижимо через UI)

**Серьёзность:** низкая → **уточнение: реально достижимо, не только гипотетический edge case.**

Проверено:
- `buildKeyPacket` (`DashAuth.kt:62-72`) действительно шифрует
  `ssid.toByteArray(Charsets.UTF_8) + aes(32 байта)` через
  `RSA/ECB/PKCS1Padding`. Для RSA-1024 максимум открытого текста для
  PKCS#1 v1.5 — 128 - 11 = 117 байт, то есть SSID длиннее 85 байт вызовет
  `IllegalBlockSizeException` в `cipher.doFinal`.
- `dispatchIncoming` (`DashSession.kt:375-405`) вызывается из
  `launchReceiveLoop` (строка 370) **без** try/catch вокруг самого вызова
  (try/catch на строках 336-347 оборачивает только `sock.receive()`, не
  `dispatchIncoming`). Исключение из `buildKeyPacket` (вызывается синхронно
  из `auth?.ingest(tlv)` на строке 389 при получении `07 00`/`07 03`)
  действительно не перехватывается и уйдёт наверх по корутине.

**Важное уточнение, не отражённое в исходном пункте:** стандартный 802.11
SSID физически ограничен 32 октетами на уровне протокола WiFi, что заведомо
меньше порога в 85 байт — то есть через **реальное** подключение к точке
доступа этот баг недостижим. Однако проверено, что в
`lib/screens/settings_screen.dart:248-259` (`_showSsidDialog`) поле
«точный SSID» — обычный `TextField` без `maxLength`/валидации длины,
значение отправляется как есть через `DashEngine.instance.setSsid(...)`.
Соответственно баг **достижим** через это поле настроек, если пользователь
вручную введёт/вставит строку длиннее 85 байт (что не требует специальных
условий — обычная текстовая вставка).

**Коррекция 3-й проверки — последствие тяжелее, чем «роняет корутину».**
2-я проверка написала «роняет корутину/приложение», не проверив scope.
Проверено:
- `OpendashDashEnginePlugin.kt:49-50` — `private val job = Job()` (**обычный
  `Job`, не `SupervisorJob`**), `scope = CoroutineScope(Dispatchers.Main + job)`;
- `CoroutineExceptionHandler` во всём модуле **отсутствует** (grep по
  `packages/opendash_dash_engine/android` — ни одного вхождения).

Следствия непойманного исключения в `rxJob` (запущен как `scope.launch(Dispatchers.IO)`):
1. исключение уходит в родительский `Job` → **отменяется весь scope плагина**,
   то есть разом умирают `sessionJob`, `rxJob`, все heartbeat'ы, `streamJob`;
2. обычный `Job` после отмены **невосстановим** — любые последующие
   `scope.launch` становятся тихими no-op, то есть дэш-движок мёртв до
   перезапуска процесса, даже если приложение выживет;
3. без `CoroutineExceptionHandler` исключение доходит до дефолтного
   обработчика Android → **краш приложения**.

Это стоит зафиксировать и как системную хрупкость (шире п. 6): **любое**
непойманное исключение в любой корутине дэша даёт тот же необратимый
результат, а не локальный сбой.

**Предлагаемое исправление:** ограничить длину SSID в UI (`maxLength`) и/или
обернуть `buildKeyPacket` в `runCatching` с переходом в `fail()`.
Системно — заменить `Job()` на `SupervisorJob()` и повесить на scope
`CoroutineExceptionHandler`, чтобы одиночный сбой не уносил весь движок.

## 8. Устаревший `errorMessage` после чистого disconnect — ПОДТВЕРЖДЕНО

**Серьёзность:** низкая (косметика).

Проверено:
- `session.onError = { msg -> publishState(errorMessage = msg) }` присваивается
  в `connect()` (`DashEngineController.kt:210`) и не сбрасывается в
  `disconnect()` (`:288-306`).
- `DashEngineController.disconnect()` вызывает `session.disconnect()`
  (строка 295) синхронно, но `DashSession.disconnect()` использует
  невызывающий `.join()` `rxJob?.cancel()` — RX-корутина, заблокированная в
  `sock.receive()`, не прерывается отменой, а получает `SocketException`
  только когда `socket.close()` реально закроет дескриптор, и это может
  произойти уже после того, как `DashEngineController.disconnect()` дошёл до
  `publishState(explicitDisconnect = true)` (строка 305).
- Эта поздняя ошибка вызывает `onError?.invoke("Lost connection to dash")`
  (`DashSession.kt` RX-catch, ~340-347) → новый `publishState(errorMessage =
  msg)` **без** `explicitDisconnect = true` (дефолт `false`), то есть новое
  raw-событие перезатирает `explicitDisconnect` обратно на `false` и
  проставляет `errorMessage`.
- В Dart (`dash_connection_alert_controller.dart:38-63`) это не приводит к
  ложному голосовому алерту, поскольку `_everStreamed` уже сброшен в `false`
  первым (легитимным) `explicitDisconnect=true`-событием, и код рано
  возвращается на `if (!_everStreamed) return;`.

**Коррекция 3-й проверки — два уточнения, оба снижают значимость до нуля.**

1. **Это гонка, а не детерминированный баг.** Формулировка «уже **после**
   `publishState(explicitDisconnect=true)`» подана как факт, но порядок не
   гарантирован ни в одну сторону: `socket.close()` происходит внутри
   `session.disconnect()` (`DashEngineController.kt:295`), а финальный
   `publishState(explicitDisconnect = true)` — на строке 305, после ещё
   четырёх вызовов (`wifiManager.disconnect()`, `locationTracker.stop()`,
   `encoder?.release()`, `DashKeepAliveService.stop()`). RX-поток вполне
   может проснуться и отработать `onError` **раньше** строки 305 — тогда
   последний `publishState` затрёт `errorMessage` обратно в `null`, и
   проблемы не возникнет вовсе. Устаревшее сообщение остаётся только при
   одном из двух возможных порядков.

2. **Поле не читает никто.** 2-я проверка написала «потенциально видимым в
   UI, если что-то его читает», не проверив. Проверено grep'ом по всему
   `lib/`: `DashEngineState.errorMessage` **не читается ни одним экраном или
   контроллером** — единственное вхождение `errorMessage` в UI
   (`settings_screen.dart:559`) относится к `AppUpdateState.errorMessage`,
   это другой класс из `app_update_controller.dart`.

Итог: текущее пользовательское влияние — **строго нулевое**, и проявляется
только в одном из двух порядков гонки. Это заготовка на будущее («не забыть,
когда появится UI ошибок»), а не дефект. Оставлять в списке стоит с
пометкой о нулевом приоритете.

**Предлагаемое исправление:** сбрасывать `session.onError` в
`DashSession.disconnect()`, либо игнорировать ошибки RX-цикла при
`_state == IDLE`.

## 10. `voiceModeProvider` стартует с устаревшим значением — ПОДТВЕРЖДЕНО (механизм), но сейчас dead code

**Серьёзность:** низкая → **на практике пока не проявляется — уточнение ниже.**

Проверено: `VoiceManager._mode` инициализируется `VoiceMode.chime` (:45),
`load()` асинхронно перезаписывает его из `SharedPreferences` (:55-64),
`voiceModeProvider` — простой `StateProvider<VoiceMode>((ref) =>
VoiceManager.instance.mode)` (:182), который действительно захватывает
значение `.mode` только в момент первого чтения и не подписан на
последующие изменения `_mode` — механизм бага в коде подтверждён.

**Уточнение, не отражённое в исходном пункте:** проверено по всему `lib/` —
`voiceModeProvider` и тип `VoiceMode` **нигде не используются** за пределами
`voice_manager.dart` (ни в одном экране, включая `settings_screen.dart`).
Формулировка исходного пункта («Экран настроек может показывать «chime»,
пока не переключит вручную») сейчас не соответствует действительности —
такого экрана/потребителя провайдера в кодовой базе нет.

### ⚠️ Коррекция 3-й проверки: диагноз «dead code» неверен

2-я проверка остановилась на «недостроенная инфраструктура». Проверка на шаг
глубже (grep `VoiceManager` / `load()` / `setMode` по всему `lib/`) даёт
другую картину — **сам `VoiceManager` активно используется**, мёртв только
слой режима:

- **живые вызовы:** `nav_loop.dart:53,102,149` (`resetTrip`, `maybeAnnounce`),
  `dash_connection_alert_controller.dart:44,61` (`announceConnectionLost`/
  `announceConnectionRestored`);
- **`VoiceManager.instance.load()` не вызывается НИ ОТКУДА** — ни в `main.dart`,
  ни в одном контроллере или экране;
- **`setMode()` тоже не вызывается ниоткуда.**

Отсюда следует, что исходная формулировка бага («провайдер захватил значение
до того, как `load()` его поменял») **описывает несуществующий сценарий**:
`load()` не выполняется никогда, значит `_mode` не меняется никогда, значит
провайдеру нечего «пропускать» — он отдаёт `chime`, и это ровно то значение,
которое поле имеет всё время работы приложения.

**Настоящее следствие — функциональное, а не косметическое.** Раз `_mode`
навсегда равен `VoiceMode.chime`, то во всех трёх местах, где он ветвится
(`maybeAnnounce` :101,113; `announceConnectionLost` :126;
`announceConnectionRestored` :137), всегда берётся ветка `else` →
`DashEngine.instance.playChime()`. То есть:
- **`VoiceMode.full` (голосовые подсказки через TTS) недостижим** — весь
  `_speak`/`_turnPhrase`/`flutter_tts`-слой, включая хендмейд-локализацию
  фраз поворотов, никогда не выполняется;
- **`VoiceMode.off` тоже недостижим** — звук нельзя отключить;
- ключ `voice_mode` в `SharedPreferences` не пишется (нет вызовов `setMode`)
  и не читается (нет вызовов `load()`).

Это не «мёртвая инфраструктура на будущее», а **работающая фича, до которой
не подведён ни один провод**: TTS-озвучка реализована и локализована, но
включить её невозможно. Формулировку пункта стоит заменить с «провайдер
стартует с устаревшим значением» на «режим озвучки захардкожен в `chime`:
`load()`/`setMode()` не вызываются ниоткуда».

**Предлагаемое исправление:** вызвать `await VoiceManager.instance.load()`
при старте (рядом с прочей инициализацией в `main.dart`) и подключить
`voiceModeProvider` + `setMode` к экрану настроек. Пока этого нет, сам
провайдер и `_prefsKeyMode` бессмысленны.

## Дополнительно (не ошибки, зоны риска) — оба пункта ПОДТВЕРЖДЕНЫ

### A. Поле `socket` в `DashSession` не `@Volatile`

Проверено: `DashSession.kt:58` — `private var socket: DashSocket? = null`,
без `@Volatile`, читается/пишется с разных потоков/диспетчеров без
синхронизации. Формально data race, практический урон низкий — согласны с
исходной оценкой.

**❌ Коррекция 3-й проверки: обоснование 2-й проверки фактически неверно.**
Утверждение «единственное поле без `@Volatile` среди соседних полей» не
соответствует коду. Полный список изменяемых полей `DashSession` **без**
`@Volatile` — их 14, а не одно:

`socket`(58), `auth`(59), `onButton`(63), `onError`(64), `sessionJob`(68),
`rxJob`(69), `projHbJob`(70), `routeCardJob`(71), `heartbeatJob`(72),
`navInfoJob`(73), `mediaInfoJob`(74), `lastLoggedIdrAcks`(94),
`lastLoggedPFrameAcks`(95), `ackCounterJob`(96).

`@Volatile` помечены только auth-флаги (`authConfirmed`, `authRetries`),
`destinationName`, media-поля и блок `nav*` — то есть примерно половина.
Так что «socket выбивается из общего стиля» — неверная посылка; здесь просто
нет единого стиля. Сам вывод (пометить `socket` как `@Volatile`) остаётся
разумным, но опирать его нужно на реальную межпоточность обращений, а не на
мнимую аномалию. Отдельно стоит заметить, что `auth` в этом смысле
безопаснее, чем кажется: и запись (`runSession`), и чтение
(`dispatchIncoming`) идут на `Dispatchers.IO`.
