## 0. Как читать и как критиковать

Каждая задача описана одинаково: **проблема → доказательство → предложение →
стоимость → риск → чем проверяется → что опровергнет посылку**. Последний пункт
существует специально: если он выполняется, задачу надо снять, а не
переформулировать.

Порядок работ — §3; отступления фиксируются в §0.1. После реализации каждого
этапа: целевые тесты, статанализ затронутого слоя (`lintDebug` для native),
ревью, отдельный коммит и остановка с показом результата человеку.
Документальная актуализация не означает выполнение этапа.

`[auto]` — локальная воспроизводимая проверка; `[ride]` — проверка человеком
на физическом дэше. Зелёные тесты не закрывают `[ride]`. Неизменяемые
контракты и их проверки перечислены в §2.1.

Ранжирование — по пользе и риску, а не по размеру файла. Оценки стоимости
не являются обещанием сроков; наличие большого класса само по себе не дефект.

## A. CI не запускается на коммит [auto]

**Проблема.** Четыре гейта (`flutter analyze`, `flutter test`,
`:opendash_dash_engine:testDebugUnitTest`, `:opendash_dash_engine:lintDebug`)
описаны и работают, но запускаются только по ночному cron и по тегу `v*`.
Сломанный `main` живёт до суток незамеченным.

**Доказательство, повторно проверено 22.10.** В `.github/workflows/`
по-прежнему только `nightly.yml` (`schedule` + `workflow_dispatch`) и
`release.yml` (`push` только для semver-тегов). Проверок на branch push или
`pull_request` нет. `core.hooksPath` не задан, в `.git/hooks/` только
`*.sample`; действующего `pre-commit`/`pre-push` нет.

**Предложение.** Отдельный workflow на branch push и `pull_request` с теми же
четырьмя гейтами, без APK и секретов. Сохранить JDK 21 и оба `flutter pub get`
(корень и `packages/opendash_dash_engine`): корневой resolve не устанавливает
dev-зависимости Pigeon локального плагина. Добавить отдельный `flutter test`
для пакета движка: корневой запуск его тесты не обходит, и в двух существующих
workflow этого шага тоже нет. Сборки APK оставить в nightly/release.

**Стоимость.** Полчаса, включая прогон и настройку кеша Gradle.

**Риск.** Практически нулевой; худшее — расход минут GitHub Actions. Если он
критичен, ограничить `paths-ignore` для чисто документационных коммитов.

**Чем проверяется / готово.** Временная ветка с намеренно сломанным тестом
приложения или пакета → красный check на push/PR; после исправления — зелёные
проверки Dart приложения и плагина, Kotlin и Android Lint. Одного YAML недостаточно.

**Что опровергнет посылку.** Если локальный обязательный хук уже запускает
полный набор гейтов, ценность падает до страховки от обхода хука. На 22.10
такого хука нет. Напоминание о ревью не заменяет выполнение проверок.

## B. Согласованность состояния камеры [auto] + [ride]

**Статус 22.10.2026.** B₁ не реализован. B₂ условный, исходная модель
«внешние команды только Main→frame» неверна. Ни один из этих пунктов не
закрывается результатами геометрического [forward-view плана](../done/2026-10-01-forward-view.md).

**Проблема.** `zoom`, `panX`, `panY` повторно читаются между dirty-сигнатурой
и отрисовкой одного кадра. Изменение между чтениями может дать сигнатуру,
не соответствующую нарисованному кадру. Это механизм, установленный по коду,
не измеренный полевой дефект. Отдельный риск — смешанная пара `panX/panY`.

**Доказательство, текущие anchors в `dash/map/MapFrameRenderer.kt`:**

- `headingUpNow` уже читается один раз (`:330–340`), с объяснением исправления
  от 16.09;
- dirty-сигнатура читает `zoom/panX/panY` (`:354–365`);
- `cameraFor` повторно читает `zoom` (`:394–420`);
- `redrawFrame` передаёт заново прочитанные `panX/panY` в padding (`:453–468`).

**B₁ — минимальное предложение.** Прочитать три значения один раз и передать
одни и те же локальные значения в сигнатуру, `redrawFrame`, `cameraFor` и
`padding`, сохранив effective tilt/pivot. Без нового объекта на каждый такт.
Это устраняет повторные чтения внутри кадра, **не** делает три чтения или
пару `panX/panY` атомарным снимком.

**B₂ — только после отдельного обоснования.** Сначала определить владельцев
состояния и атомарные переходы; не заменять поля механически на
`MutableStateFlow.value = old.copy(...)`. KDoc `DashCameraState.kt:7–19`
уже предупреждает о потере конкурентных изменений при таком подходе.

| Состояние | Текущее владение |
|---|---|
| `zoom`, `headingUp` | Main пишет; Main и frame читают |
| `panX`, `panY`, `followMode` | Main меняет команды; frame меняет через `releasePanIfIdle` |
| `lastManualPanAt` | Main пишет, frame читает |
| `lat`, `lng` | Frame-owned, `@Volatile` уже нет |
| `heading` | Frame пишет, Main читает для compass fallback |
| `initialised` | Frame устанавливает; Main сбрасывает в `beginStream` и читает |

Опоры: `DashCameraState.kt:109–204,250–346`, публикация в
`DashEngineController.kt:1528–1572`, frame-вызовы `:254,298–304` в рендерере.
Прежнее предложение «снять volatile с собственного состояния» целиком
неприменимо; `DashInputs` не готовая замена двухстороннему владению.

**Стоимость.** B₁ — локальное изменение плюс regression-сценарий.
B₂ — отдельное проектирование; прежняя оценка по аналогии с `DashInputs`
не учитывала обратные записи frame.

**Риск.** Изменить pan/idle-release либо потерять конкурентную команду.
Гарантии «исправится через 250 мс» нет: fps меняется, снапшоты пропускаются.

**Чем проверяется / готово.** В `DashCameraStateTest` уже 13 сценариев
границы idle 8 с, follow/pan, zoom/floor и `beginStream`; в `DashCameraTest`
9 сценариев геометрии. Это не проверки межпоточной согласованности.
Для B₁ нужен детерминированный сценарий изменения значений между стадиями
кадра и совпадения dirty/render. Для B₂ — сценарии interleaving manual-pan/
idle-release и `recenter`, затем `[ride]` pan/zoom/follow с указанным способом
управления. В app ручной пан не подключён; не превращать его подключение
в скрытую задачу B. Полевое подтверждение pivot/padding к B не переносить.

**Что опровергнет посылку.** Для B₁ — доказанное отсутствие повторных чтений
или невозможность изменения между ними. Для B₂ — отсутствие неприемлемых
переходов после B₁ либо явно принятое человеком остаточное рассогласование.
Само отсутствие визуального дрожания не доказывает атомарность; решение
не делать B₂ фиксируется с причиной, а не подменяется обещанием «всего один кадр».

## C. ❌ Неатомарные счётчики телеметрии — снята 24.09.2026 [auto]

**Исходная посылка опровергнута:** инкременты выполнялись на Main,
конкурирующих `++` не было. Это отклонение сохраняется, не «выполнено».

**Уточнение 22.10.2026.** Описание «теперь достаточно volatile» устарело.
С 29.09 счётчики вынесены в `SnapshotCounters`: пять `AtomicLong`,
`incrementAndGet`, оконный `getAndSet(0)` и lock для согласования session totals.
Причина другая: инкременты по-прежнему Main-only, но `drainCounters()` вызывается
с `dash-frame`. Старые накопительные totals ошибочно выдавались за показатели
каждого окна — см. `SnapshotCounters.kt:8–32` и
[`spec/frame_pipeline.md`](../../spec/frame_pipeline.md).

`MapSnapshotProvider.kt:39–44` явно исключает drain из Main-only контракта.
`SnapshotCountersTest` содержит пять последовательных сценариев окон,
session totals и reset; межпоточного stress proof здесь нет.
Появление atomics не подтверждает старую гипотезу гонки инкрементов.

Исходный текст ниже сохранён как историческая ошибка и не является заданием:
`withTimeoutOrNull` возобновлял корутину на том же dispatcher, что и capture.

**Проблема (как была сформулирована).** Счётчики в `MapSnapshotProvider` объявлены как `@Volatile var` и
увеличиваются оператором `++`. `@Volatile` даёт видимость, но не атомарность
read-modify-write: при инкременте из двух потоков часть событий теряется.

**Доказательство.** `dash/map/MapSnapshotProvider.kt` — объявления в строках
109, 126, 137, 141, 152 (`timeouts`, `skipped`, `abandoned`, `errors`,
`rebuilds`); инкременты в строках 262, 304, 308, 327, 390, 401, 409 — то есть
из нескольких мест, включая обработчик таймаута и колбэк снапшоттера.

**Предложение.** `AtomicLong` (или `LongAdder`) с `incrementAndGet()`. Тип
значения на выходе не меняется, читатели телеметрии не затрагиваются.

**Стоимость.** Полчаса на всё, включая проверку остальных счётчиков в движке на
тот же паттерн.

**Риск.** Нулевой.

**Чем проверяется.** Компиляция и существующие тесты; содержательно —
сравнение числа строк `[map]` в ride-файле с итоговым счётчиком за ту же
сессию.

**Что опровергнет посылку.** Если доказать, что все инкременты каждого
конкретного счётчика происходят на одном и том же потоке (`dash-frame`), то
`@Volatile` достаточно и менять нечего. Я этого не доказывал и не опровергал —
**это первое, что надо проверить**, потому что от ответа зависит, нужна ли
задача вообще. Подозрение основано на том, что строка 409 (`timeouts++`) живёт
в обработчике таймаута, который по смыслу не обязан быть на потоке кадра.

Отдельно стоит отметить иронию: эти счётчики заведены ровно затем, чтобы
измерять здоровье конвейера. Молча недосчитывающий счётчик хуже отсутствующего.

## E. Декомпозиция lifecycle контроллера — условно [auto] + [ride]

**Статус 22.10.2026: отложено до конкретного основания.** Не считать
выполненной, но и не превращать метрики в обязательный рефакторинг.

**Проблема.** В контроллере остаются orchestration и несколько различных
lifetimes. Из одного числа `Job` не следует необходимость общего владельца.

**Доказательство.** `DashEngineController.kt`: 1578 строк, 48 деклараций
функций класса, 10 `Job?`, четыре `@Volatile` (старый срез: 1492/47/10/4).
Уже существуют `FrameStreamer`, `MapFrameRenderer`, `DashCameraState`,
`StreamThreads`, `DashInputs`, `ConnectionFsm` и одноразовая `DashSession`;
выделять кадровый цикл заново не нужно. Архитектура —
[`spec/frame_pipeline.md`](../../spec/frame_pipeline.md), историческое
выделение — [закрытый план конвейера](../done/2026-09-16-frame-pipeline.md).

Остаток: `standDown`, `teardown`, `dispose`, `startStream`/остановка и
исполнение FSM effects. Jobs имеют разные сроки жизни: controller feeds,
stream, соединение (`memJob`), состояния auth/settle/give-up.
`teardown` намеренно не обнуляет `streamJob`: следующий старт обязан
дождаться предыдущего. Общий «сброс всех jobs» способен это сломать.

**Предложение.** Только при подтверждённой проблеме ownership — сначала
сценарии construction failure, cancel-before-first-dispatch, reconnect,
dispose; затем минимальное выделение orchestration, не новый слой ради размера.
Самостоятельный `MediaBridge` здесь не проектировать:
[мультимедийный план](2026-10-04-multimedia-support.md) уже владеет writer,
replay/reconnect и cleanup медиа. Его реализация ещё не начата.

**Стоимость.** Зависит от доказанного дефекта и выбранной границы; прежняя
«неделя-полторы на три выделения» не относится к текущей архитектуре.

**Риск.** Высокий: потерять порядок cancel/join и отправить данные старого
стрима в новый. Механическое объединение разных lifetimes запрещено.

**Чем проверяется / готово.** `FrameStreamerTest` уже проверяет цикл/rebuild/
release; `ConnectionFsmTest` и `DashSessionTest` — effects/farewell.
Прямых сценариев orchestration контроллера не найдено: они нужны до
изменения границ; после — `[ride]` reconnect/disconnect и teardown без регресса.

**Что опровергнет посылку.** Если конкретного ownership-дефекта или нужной
точки расширения нет, а media-изменения помещаются в их отдельный план,
E снимается. Читаемый большой класс и десять разных jobs сами по себе
не аргумент за новый `StreamController`.

## F. Политика проглоченных исключений [auto]

**Статус 22.10.2026.** Массовая обёртка по-прежнему отклонена; осталось
соглашение. Узкое правило «без обработки только освобождение ресурсов»
не соответствует текущим намеренным best-effort путям.

**Проблема.** Не количество `runCatching`, а отсутствие ясного различия
между допустимой потерей best-effort операции и потерей основного действия.

**Доказательство.** В исходном срезе 24.09 число 66 было артефактом grep:
разбор скобок дал 73 сайта, 35 с обработкой и 38 без. Это исторические числа,
сегодня не пересчитывались. Уже тогда `Log.*` и `setThreadPriority()` не были
освобождением ресурса. Сейчас есть явные дополнительные исключения:

- `DashEventSink.emit` допускает исчезнувший Pigeon sink; причина записана в KDoc;
- `RideDiagnostics.raw` и `fromFlutterDeferred` допускают отказ записи
  диагностического файла;
- `OpendashDashEnginePlugin.drainRideErrors` ограничивает ожидание writer,
  а `rideError` подавляет отказ постановки диагностической записи;
- `StreamThreads` допускает отказ повышения приоритета, фактический приоритет
  выводится отдельным `report()`.

Это не доказательство отсутствия ошибок во всех обработчиках и не повод
считать каждый из этих путей очисткой.

**Предложение.** Зафиксировать соглашение: намеренный best-effort
(освобождение, диагностика, необязательная настройка, доставка в исчезнувший
sink) требует понятной причины и границы допустимой потери; сбой основного
действия — наблюдаемого результата/ошибки. Не вводить `ignoringFailure`,
не оборачивать все сайты и не логировать ошибки логирования рекурсивно.

**Стоимость.** Малое документальное изменение; массовый обход не входит.

**Риск.** Общее правило может узаконить потерю полезного действия под видом
best-effort; поэтому одного имени обёртки недостаточно.

**Чем проверяется / готово.** Соглашение записано и применимо к перечисленным
реальным примерам без фиктивных исключений «это тоже освобождение ресурса».
Ревью документа, а не счётчик `runCatching == 0`.

**Что опровергнет посылку.** Если это различие уже однозначно закреплено
действующими правилами, нового соглашения не нужно. ❌ 24.09.2026:
первоначальный массовый обход и обёртка сняты после разбора всех 38 сайтов;
это решение сохраняется, прежний критерий «довести число до нуля» не действует.

## H. Совместимость БД между сборками [auto]

**Статус 22.10.2026: открыта, решение исправлено.** Риск downgrade
подтверждён по исходникам resolved sqflite, не воспроизведён на устройстве.

**Проблема.** В `lib/data/app_database.dart` один `opendash.db`, версия 2,
миграция v1→v2 создаёт `installed_pack`; `onDowngrade` отсутствует.
Каналы stable/nightly выбирают разные источники обновлений, но общей
политики совместимости схем при переходах между сборками нет.

**Доказательство.** В используемом `sqflite_common 2.5.11`,
`lib/src/database_mixin.dart:1132–1173`, downgrade вызывает callback только
если он задан, после чего `setVersion(options.version!)` записывает меньший
`PRAGMA user_version`. Успешный no-op callback ведёт к тому же результату.
`pubspec.lock` и `.dart_tool/package_config.json` указывают именно эту версию.
`sqlite_garage_repository_test.dart` и `installed_packs_repository_test.dart`
проверяют fresh DB/CRUD, не миграции и сохранность данных между версиями.

**Условный сценарий.** Если установить старую сборку поверх новой с сохранением
данных и затем вернуться, номер схемы может оказаться меньше фактической схемы,
и upgrade запустится повторно. Реализуемость установки зависит от versionCode,
подписи и установщика; переключатель канала сам не меняет схему.
В checkout v2, но схемы опубликованных APK в этой сверке не проверялись.
Утверждения «обе линии сейчас v2» и «сломается за два нажатия» сняты.

**❌ 22.10.2026 отклонено прежнее исправление «три строки».**
`CREATE TABLE IF NOT EXISTS` предотвращает лишь конфликт имени, не проверяет
колонки, constraints, индексы и семантику данных. No-op с логом добавляет
наблюдаемость, но не защищает версию. Отсутствие `IF NOT EXISTS` нормально
для строго однократной миграции; blanket-идемпотентность не решение.

**Предложение — до следующего повышения версии схемы:**

1. Зафиксировать схемы поддерживаемых сборок. Первым шагом проверить настоящий
   v1→v2 и файловый downgrade/повторный upgrade fixture с закрытием handles,
   чтением `user_version`, структуры и содержательных пользовательских строк.
2. Выбрать и записать поддерживаемую матрицу переходов. Без доказанной
   backward compatibility безопасная исходная политика — отклонять
   несовместимое открытие без изменения/удаления БД, с понятным сообщением.
   Поддерживаемый downgrade требует проверки старых readers **и writers**.
3. Учесть rollout: новый callback не защищает уже выпущенный старый APK.
   Политику установки/обновления описать рядом с каналами в
   [`spec/settings_screen.md`](../../spec/settings_screen.md).

`onDatabaseDowngradeDelete` не применять: он стирает пользовательские данные.
Запрет открытия также требует UX-решения; это не готовый безопасный фикс
одной строкой и не основание сейчас менять поведение приложения.

**Стоимость.** Characterization отдельно от реализации политики; оценка
«полдня на три строки» отозвана до определения поддерживаемой матрицы.

**Риск.** Высокая цена потери данных; даже сохранная БД не делает отказ
запуска приемлемым без понятного восстановления.

**Чем проверяется / готово.** Поддерживаемые переходы сохраняют строки
поездок/расходов/паков и корректные repository reads/writes; неподдерживаемые
предсказуемо отказывают, не меняя версию, схему и данные. «Не бросает» недостаточно.

**Что опровергнет посылку.** Доказанное исключение установки несовместимой
сборки поверх этих данных снимает именно риск downgrade; обычный тест v1→v2
всё равно нужен. Одинаковая схема двух текущих каналов не гарантирует
совместимость будущих и уже выпущенных сборок.

  при переносе кода сохранять. Спеки обновлять вместе с изменением поведения.
- Не включать заново отклонённые шумные правила анализатора
  (`discarded_futures`, неработающий CLI `riverpod_lint`) под видом уборки.
- Если тест просит изменить ожидание, сначала проверить контракт и источник;
  намеренные отличия от оригинального APK не считать ошибкой автоматически.
- `[ride]` закрывает человек с указанием сборки/устройства/лога, по
  [порядку полевой проверки](../../docs/ON_HARDWARE_VERIFICATION_RU.md).

### Явные не-цели

- **Не удалять `ProjectionOn` как уборку.** Отдельная команда сейчас не
  вызывается production-сценариями, её форма покрыта golden. Но TLV
  `06 05 55` реально отправляется в составных `RouteCard`/`ActiveNav`;
  старое утверждение «не отправляется никогда» неверно. Причинная связь
  с отказом от режима обоев не подтверждена независимым источником.
- **`panBy` не удалять и не подключать в рамках аудита.** Сквозной Pigeon API
  существует, вызовов из app `lib/` нет. Незакрытый пункт «если подключён»
  в hardware checklist — не обещание реализации и не полевое доказательство.
- **Не переписывать генерируемые файлы l10n** (`app_localizations*.dart`,
  3.3k строк) — это вывод инструмента.
- **Не вводить detekt/ktlint.** Android Lint уже настроен и стоит в CI; второй
  линтер добавит шум без новых классов находок. (Утверждение спорное — если
  разбор считает иначе, интересно услышать, какие именно правила detekt поймали
  бы что-то, чего нет сейчас.)
- **Не менять media wire-контракт под видом уборки.** Baseline с 20.10 —
  ICU→ASCII, до 20 байт после расширения; порядок `title, album, artist`,
  отсутствие NUL после artist, 1 Hz и приоритет кнопок сохраняются.
  Изменения и независимые hardware-гейты принадлежат
  [мультимедийному плану](2026-10-04-multimedia-support.md), не E/G.

## 5. Что считать успехом всего плана

- A ловит сломанный branch push/PR, включая тесты локального Dart-плагина.
- B₁ исключает повторные несогласованные чтения для dirty/render; B₂ либо
  обоснован и проверен отдельно, либо явно отклонён, не «сделан на всякий случай».
- D закрывает перечисленные оставшиеся переходы, а не просто добавляет файлы тестов.
- H доказывает сохранность данных и корректное поведение версий, не одно отсутствие исключения.
- F/G закреплены как применимые правила без массовой косметической переделки.
- E выполнен только при доказанной оставшейся проблеме; отказ по собственной
  опровергающей посылке тоже завершает задачу. C остаётся отклонённой.
- Открытый `[ride]` не позволяет архивировать весь план как выполненный.
  I — информационный срез, не условие обновить все зависимости до latest.

## 6. Границы проверки

Перечислено, чтобы разбор знал границы утверждений:

- **Производительность.** Ни одного замера. Все суждения о кадровом цикле —
  из чтения кода и существующей документации.
- **Dart-часть UI.** Размеры экранов из исходного среза (693/557 строк)
  не актуализировались и не доказывают архитектурный дефект; UI не разбирался.
- **Сборка.** Дубликаты транзитивных зависимостей и размер APK — не смотрел.
  Версии пакетов — см. I.
- **Безопасность.** `dart_defines.local.properties` в `.gitignore` (проверено
  24.09, и корневой, и `android/`); дальше аудита не было.
- **Работа с БД.** Миграции повторно разобраны 22.10 — см. H. Запросы и
  индексы не аудировались.
- **Покрытие в процентах.** `dart-collect-coverage` не запускался.
  Для D прочитаны существующие поведенческие сценарии; это не измерение
  покрытия и не доказательство их прохождения на текущем дереве.

## 7. Одно наблюдение не про код

Проект систематически находит собственные ошибки чтением, а не инструментами:
три неверные подписи TLV, три дефекта конкурентности из записи в CLAUDE.md, —
всё это нашли ревью и повторный разбор, а не тесты и не линт. Это работает, но
масштабируется плохо и зависит от одного человека. A и остаток D переносят
часть нагрузки на машину. B требует и механической проверки согласованности,
и полевого результата; C напоминает об обратном риске — объявить гонку,
не проверив владельца состояния.
