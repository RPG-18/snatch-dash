# План: OSM extract → PMTiles

Конвейер подготовки оффлайн-тайлов (см. [`tools/CLAUDE.md`](../CLAUDE.md)).
Источник правды по тому, какие страны/регионы обрабатываются —
[`regions.yaml`](./regions.yaml). Любой скрипт конвейера обязан пропускать
страны с `enabled: false` — они в конфиге только как заготовка на будущее, без
реальной обработки.

## Статус

- **Россия** — единственная включённая страна (`enabled: true`, `mode: subjects`).
  Режется на субъекты РФ.
- **Абхазия, Азербайджан, Армения, Беларусь, Грузия, Казахстан, Кыргызстан,
  Молдова, Таджикистан, Узбекистан, Украина** — зарегистрированы в
  `regions.yaml` как `mode: whole`, но `enabled: false`. Обработка по ним
  сознательно не реализуется на этом шаге — только резервируем код страны и
  источник данных, чтобы включать по одной, когда дойдут руки, без переделки
  формата конфига.

## Шаги конвейера (для страны с `enabled: true`)

1. **Скачать исходный `.osm.pbf`** — из `source` в `regions.yaml` (Geofabrik),
   вручную, в `downloads/<iso>-latest.osm.pbf`. Скрипты сами ничего не тянут
   по `source` — это просто ссылка, куда сходить (см. «Как запустить» ниже).
2. **Границы** (`fetch_boundaries.py`, только для `mode: subjects`) — тянем
   через Overpass API релации `admin_level = subject_admin_level` внутри
   страны и сохраняем каждую как отдельный `.osm`-файл (не geojson — см.
   ниже, почему), называем по тегу `ISO3166-2` в нижнем регистре
   (`RU-MOW` → `polygons/ru-mow.osm`). Там, где тега нет — релация
   пропускается с предупреждением, сопоставление вручную не реализовано.
   Для `mode: whole` этот шаг не нужен вообще — граница не нужна, скачанный
   файл уже обрезан по стране Geofabrik'ом.
3. **Конфиг для osmium** (`build_extract_config.py`, только для
   `mode: subjects`) — по файлам `polygons/<iso>-*.osm` строит один
   `extracts/<iso>-extracts.json` на всю страну (не по вызову на регион —
   иначе на файле размером с `russia-latest.osm.pbf` это в 80+ раз дольше).
4. **Нарезка** (`split.py`):
   - `mode: subjects` — `osmium extract --strategy=smart -c <iso>-extracts.json downloads/<iso>-latest.osm.pbf`,
     на выходе `extracts/<iso>-<subject>.osm.pbf` (`ru-mow.osm.pbf`, `ru-ta.osm.pbf`, …).
   - `mode: whole` — просто копирует `downloads/<iso>-latest.osm.pbf` в
     `extracts/<iso>.osm.pbf`, без osmium.
5. **Тайлы** (`build_pmtiles.sh`) — planetiler по каждому файлу из
   `extracts/`, на выходе `out/<iso>/<код>.pmtiles` (см. «Иерархия `out/`»
   ниже). Из параметров planetiler явно заданы:
   - `--languages=ru,en` — приложение двуязычное (RU/EN), схема OpenMapTiles
     по умолчанию иначе тянет `name:*` на всех языках.
   - `--maxzoom=14` — стандартный потолок детализации схемы OpenMapTiles. В
     отличие от растра (`TileProvider` префетчит 11-20 — отдельные наборы
     картинок на каждый зум), у векторных тайлов зум сверху не диапазон,
     который нужно печь целиком: рендерер (MapLibre и подобные) сам
     оверзумит выше maxzoom, масштабируя последний сгенерированный тайл, без
     новых данных с сервера. `minzoom` не трогали — вниз пирамида нужна вся,
     на разных зумах в схему попадают разные объекты.

   Память/потоки, транслитерация — не настраивались, дефолты planetiler;
   вернуться к этому при первом реальном прогоне, если не хватит.
6. **Индекс** (`build_index.py`) — после сборки тайлов пройтись по `out/` и
   построить `out/index.json` (см. ниже) — размер, sha256 и время генерации
   для каждого файла, чтобы телефон мог сверить локальную копию с текущей.
7. **Публикация** (отдельный скрипт, не описан здесь) — залить локальный
   `out/` во временный каталог на сервере, затем выполнить атомарный `move` в
   боевой каталог через API хостинга. Сборка (шаги 1–6, целиком локальные,
   результат — каталог `out/`) и публикация — разные шаги с разной
   ответственностью, публикация не входит в этот план.
8. **Регенерация** — весь конвейер (шаги 1–7) гоняется целиком заново раз в
   неделю, с удалением каталога `out/` перед пересборкой — то есть каждый файл
   каждый раз собирается с нуля, инкрементальной пересборки нет и не
   планируется. Отдельная логика поиска/чистки «осиротевших» файлов от
   выключенных/переименованных регионов не нужна: `out/` каждый раз пустой
   перед стартом.

## Иерархия `out/`

Подкаталог на страну, имя файла внутри — тот же код, что уже используется как
имя `.pmtiles` (без изменений относительно предыдущего шага, просто он теперь
не лежит в одной плоской куче с остальными ~90 файлами):

```
out/
  index.json
  ru/
    ru-mow.pmtiles
    ru-mos.pmtiles
    ru-ta.pmtiles
    ...
  by/
    by.pmtiles
```

Почему подкаталог на страну, а не плоский список — как только включим ещё
хотя бы одну-две страны из `regions.yaml`, в одном каталоге окажется ~90+
файлов вперемешку с уникальными по стране именами; разложить по `<iso>/`
дешевле сделать сразу, чем потом. Плюс так удобнее частичная синхронизация:
если пересобрали только один субъект РФ, трогать/заливать нужно только
каталог `ru/`, а не весь `out/`.

## `index.json`

Один манифест на весь `out/`, сгруппированный по странам (та же группировка,
что в `regions.yaml`) — телефон получает готовую структуру «страна → список
регионов» без сборки на своей стороне:

```json
{
  "version": 1,
  "generated_at": "2026-08-30T13:00:00Z",
  "file_count": 2,
  "total_size": 251658240,
  "countries": [
    {
      "iso": "ru",
      "mode": "subjects",
      "regions": [
        {
          "code": "ru-mow",
          "path": "ru/ru-mow.pmtiles",
          "size": 41943040,
          "sha256": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08"
        }
      ]
    },
    {
      "iso": "by",
      "mode": "whole",
      "regions": [
        {
          "code": "by",
          "path": "by/by.pmtiles",
          "size": 209715200,
          "sha256": "3a7bd3e2360a3d29eea436fcfb7e44c735d117c42d1c1835420b6b9942dd4f1"
        }
      ]
    }
  ]
}
```

Поля:

- `version` — версия схемы самого `index.json` (не данных внутри), чтобы
  можно было менять формат, не ломая старые клиенты молча.
- `generated_at` — один UTC-таймстемп на весь файл (ISO 8601), время сборки
  индекса, а не отдельных `.pmtiles` — так и просили: «время, когда он был
  создан». Заодно это и есть дешёвая проверка «менялось ли вообще
  что-нибудь» (см. ниже).
- `file_count` / `total_size` — агрегаты по всем регионам, чтобы UI показал
  «скачать всё — N файлов, X ГБ» без суммирования на телефоне.
- `code` — тот же код, что и имя файла без расширения (`ru-mow`, `by`) —
  не придумываем второй идентификатор рядом с именем файла.
- **Намеренно нет `name`** — приложение двуязычное (RU/EN, `AppLocalizations`,
  см. [`lib/l10n/`](../../lib/l10n)), а генератор тайлов не должен знать про
  локализацию. Отображаемое имя по `iso`/`code` (страна, субъект РФ) — таблица
  на стороне приложения, не в этом конвейере.
- `sha256` — а не md5/crc32: не про криптостойкость, а чтобы не заводить в
  проекте второй хеш ради «покороче» — sha256 и так есть из коробки в любом
  рантайме (Python `hashlib`, Dart `crypto`/`package:crypto`), больше файла
  на 100+ МБ не имеет значения.
- `path` — относительно `out/` (совпадает со структурой каталогов выше), не
  абсолютный URL — базовый хост/CDN клиент подставляет сам.

**Как это использует телефон** (упрощённый вариант оптимистической
блокировки):

1. Скачивает только `index.json` (лёгкий) и сравнивает его `generated_at` с
   тем, что сохранено с прошлой проверки. Не изменился — всё свежее, дальше
   можно не ходить.
2. Изменился — по каждому локально установленному паку сравнивает `sha256` из
   нового `index.json` с сохранённым при прошлой установке. Расхождение —
   значит именно этот файл обновился на сервере, качаем заново; остальные не
   трогаем.
3. После докачки `.pmtiles` пересчитывает sha256 полученных байт и сверяет с
   `index.json` — это чистая проверка целостности самой закачки (что просили
   в п.1 обсуждения), не про определение, что изменилось. Не сошлось — файл
   битый/докачался не полностью, повторить закачку.

Отдельно стоит иметь в виду: planetiler может писать в метаданные тайлсета
время своей сборки, из-за чего `sha256` пересобранного файла отличается от
предыдущего, даже если сами данные OSM не поменялись. При еженедельной
пересборке «с нуля» (см. шаг 8 выше) это и так означает переустановку всех
паков каждую неделю по дизайну — отдельно бороться с этим (стабилизировать
метаданные, заводить второй хеш «источника») сейчас не нужно.

## Скрипты

```
tools/planetiler/
  regions.yaml            # конфиг стран/регионов
  plan.md                 # этот файл
  requirements.txt        # pip-зависимости (PyYAML — единственная)
  .gitignore              # downloads/ polygons/ extracts/ out/ — не в git
  common.py               # общее: чтение regions.yaml, пути, логирование
  fetch_boundaries.py     # Overpass -> polygons/<code>.osm, только mode: subjects
  build_extract_config.py # polygons/<iso>-*.osm -> extracts/<iso>-extracts.json
  split.py                # osmium extract (subjects) / копирование (whole) -> extracts/*.osm.pbf
  build_pmtiles.sh        # planetiler по extracts/*.osm.pbf -> out/<iso>/<код>.pmtiles
  build_index.py          # обход out/, sha256+size -> out/index.json (атомарно)
  downloads/              # сырые .osm.pbf с Geofabrik — кладутся вручную, не в git
  polygons/               # границы субъектов (.osm), генерируются fetch_boundaries.py, не в git
  extracts/               # промежуточные .osm.pbf по стране/субъекту, не в git
  out/                    # итоговые .pmtiles + index.json, не в git
```

`split.py` и `build_index.py` — на Python, а не shell, чтобы конвейер не
зависел от bash/zsh и одинаково работал под Windows/macOS/Linux. `build_pmtiles.sh`
остался на bash — это просто цикл вызовов одной Java-команды, переписывать
не просили.

Границы субъектов (`fetch_boundaries.py`) сохраняются в формате `.osm`
(OSM XML), не `geojson`, как обсуждалось изначально: `osmium extract` умеет
сам собирать (мульти)полигон границы из релации в таком файле — не нужно
самостоятельно собирать геометрию outer/inner колец средствами Python.

Все скрипты умеют `--only <iso[,iso...]>` (ограничиться одной страной,
удобно для тестового прогона на `ru` без реального Overpass/osmium под рукой)
и `--verbose`; `--help` на каждом — короткая справка.

## Как запустить (для России, `enabled: true`)

```bash
cd tools/planetiler
pip install -r requirements.txt

# 1. Скачать вручную — regions.yaml.ru.source -> downloads/ru-latest.osm.pbf
mkdir -p downloads
curl -L -o downloads/ru-latest.osm.pbf https://download.geofabrik.de/russia-latest.osm.pbf

# 2. Границы субъектов через Overpass (медленно — ~85 последовательных
#    запросов с паузой между ними, чтобы не долбить публичный API)
python3 fetch_boundaries.py --only ru

# 3. Конфиг для osmium
python3 build_extract_config.py --only ru

# 4. Нарезка (нужен установленный osmium-tool)
python3 split.py --only ru

# 5. Тайлы (нужен установленный planetiler.jar)
PLANETILER_JAR=/path/to/planetiler.jar ./build_pmtiles.sh

# 6. Индекс
python3 build_index.py --only ru
```

Публикация на сервер (шаг 7 из «Шагов конвейера») сюда не входит — см. «Что
не входит в этот план».

## Открытые вопросы (до включения обработки конкретной страны)

- **Абхазия** [DEFERRED] — нет своего ISO 3166-1 кода и Geofabrik-экстракта
  (территория внутри грузинского). Нужно решить источник данных/границы
  отдельно, прежде чем ставить `enabled: true`. Разбираться будем, когда
  реально понадобится включать эту страну, не раньше.
- **Украина** [DEFERRED] — в OSM есть альтернативные релации границы для
  части территории (Крым, зона конфликта). Нужно осознанно выбрать, какую
  использовать, до включения. Разбираться будем, когда реально понадобится
  включать эту страну, не раньше.
- **Источники (`source`) для остальных стран** в `regions.yaml` не сверялись
  живым запросом к Geofabrik на момент написания — проверить актуальность
  ссылки перед первым включением любой из них.

## Что не входит в этот план

- Обработка (`enabled: true`) любой страны, кроме России.
- **Публикация на сервер** (шаг 7) — скрипт загрузки во временный каталог +
  API атомарного `move` в боевой каталог. Здесь только зафиксирован контракт
  (локальная сборка кладёт готовое в `out/`, дальше это отдельная зона
  ответственности), сама реализация — не сейчас.
- **Клиентская часть на телефоне** — сравнение `index.json`, скачивание,
  выбор паков пользователем, лимит/освобождение места под них (в отличие от
  растрового кэша `TileProvider` с его 200 МБ бюджетом, эти паки на порядки
  крупнее). Осознанно отложено на следующую итерацию, когда будут готовы
  реальные данные и станет виден их фактический размер.
